## What changed against the published build (deploy 6abd6d62)

Train R1e is cumulative on R1d. R1d added the groups CLOCK, DATA, MON, ANIM, POLISH, PERF2, PERF3 and BASE1863 with their page groups; R1e adds PERF4 and ACC with the page groups PG-zperf4 and PG-zacc, a changed ANIM (`ANIM@R1e.json`, `ANIM+mon@R1e.json`) and the build feature `<GROUP>@<TRAIN>.json`. In plain terms, to a visitor:

* corrected clock and chronology data (69 served data files);
* the restored monument layer (the Walkthrough and its Monuments tab as published); a click on a unit mark that lies over a monument dot now selects the unit (R1e);
* the new animation layer: event, story and unit cards that never stand on each other or on controls, and the legend "What the marks say" (R1e: a card never ends up above the map or on the toolbar);
* the 1863 base map, with all its road names (R1e fixes road names missing on about a third of loads of the intermediate build);
* much faster phone loading (R1e: `/` phone blocking time at 4x CPU 83 to 129 ms median against 424 ms on R1d and 391 ms on the published build; the first day jump on a phone answers in 64 to 96 ms against 144 to 232 ms);
* corrected casualty rates: 107th Pennsylvania 255 men, 64.7 % (was 135.2 %), 6th US Cavalry no rate with the reason, and the Regiment and Report pages never print a rate above 100 %;
* the layout polish of R1d (1024 px, phone landscape, accessibility names, tap targets), the rebuilt tutorial PDF (cover "Updated October 2026", no release label), the Turning Points moment "Culp's Hill Retaken" at about 7:05 AM on July 2.

The complete patch list is `release/R1e/anchors.json`; R1e adds 19 patches over R1d.

## What is not clean (read this before the passes)

1. **Check 4 fails on the final bytes: 2 defects in pass 1** (item 5 of the table above): the first click on the Virtual Walkthrough and on the Monuments button on the desktop map screen are 50 to 70 ms tasks (limit 50). They sit around the limit, so a run can miss them (scratch run 2 of the earlier zip did), but 4 of the 5 sweeps of the desktop app on this build had at least one. Without a change to how those two draw their first frame, the eight consecutive clean passes cannot be reached. The other defects of the earlier report are fixed (items 1 and 2) or were measured against the wrong event (item 3, an audit-tool change the owner should confirm).
2. **Check 5** was clean on the final bytes in pass 1 (phone TBT max 130 ms), in the earlier full run and in a 350-load repeat, but a heavy tail on phone `/ground-remembers` (Mapbox library tasks: map constructor, style load, first render, placement) had been seen at about 1 load in 20 to 30 above 200 ms; eight passes will hit it with some probability. No fix was found that keeps the look.
3. **T0-ANIM-B11** (a spec, not a release gate: `tools/accept` never runs `anim.spec`) passes 3 of 5 whole runs; the 8x allowance of 3 engine-attributed long tasks is below the engine's own distribution on the 4x phone. Not fixed, no limit raised; the ways forward are owner decisions (decision R6).
4. **Waivers**: the owner's yes for the 56 basis-B entries is not recorded; 24 depend on provisional decisions.
5. **Coverage**: Chrome on one Windows machine only; no real iPhone or Android, no Safari or Firefox, no real Netlify deploy. `--full` accuracy was not run on this zip.

## The eight passes: the exact command

Nothing in the tree may change between the start and the end of the run (the runner records the zip, the harness, the baseline and `release/R1e/dist` digests before and after every pass and aborts if any moves). Run it on a quiet machine, with no other test, build or browser work in parallel: check 5 is a timing check.

```
cd C:\Users\mlege\gettysburg-map
node tools/accept/run_eight.mjs --candidate deliver/gettysburg-R1e-c2afeeda-PRODUCTION.zip --baseline baseline/dist --soak-seconds 600
```

* Candidate = the PRODUCTION zip (sha256 above). Passes are strictly sequential, each a fresh unzip and fresh browser profiles; the run stops at the first pass with a defect or a check that did not run. A pass takes roughly 80 minutes (check 4 about 29, 6 about 22, 5 about 14 with the 600 s soak, 7 about 7, 3 about 4); eight passes about 11 hours. Earlier pass files are archived to `docs/accept/passes/archive/<time>/` and the log is `docs/accept/EIGHT-PASS-LOG.md`.
* **Check 1** compares the zip's hash with the previous pass's hash (`pass-N-1.json`), with the `.sha256` file next to the zip, and repacks `release/R1e/dist` with `tools/ship/pack_zip.py` (production variant, from the zip's name). Pass 1 has no previous pass and uses the sidecar and the repack; every pass from 2 on also needs the previous pass's file, which the eight-pass run writes. To run check 1 alone for a pass N after N-1: `node tools/accept/run_pass.mjs --candidate deliver/gettysburg-R1e-c2afeeda-PRODUCTION.zip --pass N --only 1 --out-dir <the folder holding pass-(N-1).json>`; or give the hash directly with `--prev-sha 30faf627...fffe0`. Both were exercised (see the checks table).
* **Check 6** needs the registered build next to the candidate: `release/R1e/` (dist, anchors.json, gate.json, manifest.json). It exists now (`python tools/t0/build.py --train R1e`, decision PK2), and the check refuses to count the candidate as the built dist unless every file is byte-identical, which it is. Do not rebuild or delete `release/R1e` during the run. `--full` (the whole `tools/t0/run_suites.mjs`, about 2.5 hours per pass) is available and not part of the command above; the subset in `tools/accept/accuracy_subset.json` is what passes 101 to 103 used.
* Not run here: `--shots`, `--cpu-throttle`, other optional switches. Real devices, Safari and Firefox are outside the harness.
