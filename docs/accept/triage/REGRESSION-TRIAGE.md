- **Waivers cannot hide a different break.** `regression_waivers.proposed.json` gives every proposed waiver its defect ids, evidence (file and line, patch id) and automated assertions evaluated by `assert_waivers.mjs`: the **patch ledger** must contain only the listed patch ids for the page (a new patch = a new difference = fail), the **lost-line and lost-control sets** must equal the documented ones, the **replacement** must be present (and for the browser checks, behave), and a **per-route pixel and page-height budget** (1.5x the observed value) must hold. ## 3. The specific questions, settled

### 3.1 `assets/InterpolationWorker-ufiwa2-e.js` (D01)

*Is the worker still used anywhere? Is it replaced by a hashed name? Does the animation lose anything?*

- **It was never used.** The published file is 672 bytes (sha256 `a44f17c2...c865b`, the value pinned in `tools/t0/trains.json:17`): an `onmessage` handler that linearly interpolates `lat`, `lng`, `bearing` (shortest arc), `strength` and `disposition` between `placementsByTick[fromTick]` and `[toTick]`. Nothing in the published build names it: `InterpolationWorker` and its hash token `ufiwa2` occur in **no** text file of `baseline/dist` (entry bundle, both chunks, `index.html`, `sw.js`, CSS, JSON), and every `new Worker(...)` in the published bundle takes a variable (Mapbox's own blob worker URL), never a literal URL. Assertions `W-file-InterpolationWorker/*` re-prove this on every candidate.
- **It is not replaced under another name.** The candidate's `assets/` holds exactly four files (entry, `HelpModal`, `BookmarkPanel`, CSS). No candidate file has that hash, and the worker's payload signature (`placementsByTick:i,fromTick:o`) occurs in none of them. The release mechanism deletes it on purpose: `tools/t0/trains.json:11` lists it as an `orphans` entry, `tools/t0/README.md:57` says "deletes the five legacy assets (entry, both chunks, CSS, orphan `InterpolationWorker-*.js`)", `docs/plan/FINAL/05-performance-to-green.md:34` ("`InterpolationWorker` (672 B) unreferenced") and `04-time-model-and-historical-accuracy.md:51` ("`InterpolationWorker` is dead code"), `ops/release-notes/R1c.md:19` lists it under "Files removed".
- **The map's animation loses nothing.** The unit motion the visitor sees in the published build is the bundle's own `requestAnimationFrame` loop (`Ed`) over `placementsByTick`, without interpolation; the candidate keeps that loop (group B changes only which tick's state it draws). The later `ANIM` group (owner decision 2026-10-05 item 5, continuous interpolation) is also main-thread code: `tools/t0/patches-next/ANIM.json` contains no `new Worker`.
- **Classification: INTENTIONAL**, no user-visible effect.

### 3.4 Dashboard lines "(52.3% casualties ⚠)" etc. (D09, D11) -- **real in R1c alone**

The published page flags, with a warning glyph and a footnote, the two corps whose engagement periods do not add up to the source file's own `total_casualties`: **U-I** (periods 6,394 vs total 6,059 = 52.3 % vs 49.6 %) and **C-CAV** (483 vs 583 = 5.1 % vs 6.1 %). Patch `PGC-dash-cards` also *newly* prints the card "Highest regimental loss rate, Confederate: 69.7 %, 26th North Carolina", a figure the plan's own re-check refutes (`08a-subpages-A-B.md:43`: the Confederate leader by rate is 8th Virginia 76.7 %); the published page never showed it (it printed the raw key and "undefined").

Measured on the full-stack scratch build `tmp/polish/pa/dist` (R1c + CLOCK + DATA + MON + ANIM + POLISH): every corps's periods now sum to its `total_casualties` (U-I 6,059 = 49.6 %, C-CAV 483 = 5.1 %), so nothing is left to flag. `W-text-dashboard` carries the assertion `source-data-consistent`, which **fails on the R1c zip and passes on the full stack**: the waiver cannot be applied to a build without DATA.

## 7. Findings about the acceptance harness itself (for the integrator; nothing under `tools/accept/` was edited)

### 7.1 Check 3 compares the candidate with the published **chooser screen**, not the published app (D44-D49)

`tools/accept/checks/c3_regression.mjs` loads each route, and for the app calls `lib.waitForApp` then `lib.chooseLayout(page, ...)`. `chooseLayout` (`tests/t0/lib.mjs:314-331`) returns `'absent'` once the app has been mounted for 1.5 s without a "Choose Your Experience" text. The published app only shows that screen after its ~3.5 s fake fast-forward intro, so the baseline is captured **at the chooser**: the "62 lost lines / 42 lost controls" of `index@390`, the 16 lines / 3 controls of `index@1440` and both index pixel diffs describe the chooser (its text, its two cards, and the desktop overlays behind it), not the application. This inflated the index defects and hid the real, much smaller differences (section 3.3, 3.6).

Recommended fix (a few lines, `tools/accept/checks/c3_regression.mjs`, function `capture`, for `mode === 'inject'` and `origin === ctx.base.url`): after `lib.waitForApp`, wait for the chooser explicitly and click through it,

```js
const ch = page.getByText('Choose Your Experience');
await ch.first().waitFor({ state: 'visible', timeout: 25000 });
await page.getByText(vp[0] < 500 ? 'Select Mobile' : 'Select Desktop').first().click();
await ch.first().waitFor({ state: 'detached', timeout: 10000 });
```

and keep `lib.chooseLayout` for the candidate (it correctly finds no chooser). `assert_waivers.mjs` already does this in `capture()`. With the fix the index rows will show only the differences listed in 3.3 and 3.6.

### 7.2 Check 3 loses the evidence it needs

The report prints at most six lost lines per route (`slice(0, 6)`), the raw JSON stores none of them, and the screenshot rows cannot say **why** a page moved. This triage had to re-capture every route to get the full lists (`tmp/triage/capture.json`, 23 routes x 2 viewports). Suggest `c.raw.text[tag] = { lost, gained, lostControls }` in `raw`, and a `layoutShift` field (page-height delta and the y of the first heading in both builds).

### 7.3 Map-page screenshots depend on tile timing (D39 camera 59 %)

The harness hides `.mapboxgl-canvas`, which leaves whatever the compositor holds behind it. On `camera@1440` the baseline shot is brown and the candidate's is black although the DOM behind the canvas is identical (`tmp/triage/camera_probe.mjs`: `#map`, `#map-wrap` transparent, `body` `rgb(10,10,20)` in both). With the canvas visible and 9 s of settling, both builds draw the same imagery, markers and controls (`evidence/camera-base.png`, `camera-cand.png`: the candidate is 9 px lower because of the shared nav). Suggest forcing `.mapboxgl-map{background:#000!important}` in the injected style, or comparing only outside the map box.

### 7.4 Waivers match by (kind, route) only

A waiver for `text` on `/dashboard` hides **any** lost line on that route, including one that is a real break. The proposed waivers therefore carry assertions (section 1, last bullet) that fix the allowed set of lost lines, lost controls and patches, and a per-route pixel/height budget; implement them in `c3` as `{ assertions }` evaluated by `docs/accept/triage/assert_waivers.mjs` (it also works standalone, below). The existing four waivers have no assertion; they are all correct (`verify_release` V3 asserts the `/diagnostics` and `/unit-rendering-reference` 404s).

### 7.5 No published-build baseline for checks 4 and 5

Checks 4, 5 and 7 only measure the candidate, so "13 input defects" and "5 performance defects" cannot be read as regressions or not. Section 9 measures the same things on both builds.
