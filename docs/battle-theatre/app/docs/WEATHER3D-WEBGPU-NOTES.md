# WebGPU path of the weather and effects layers

Written 2026-11-13, extended 2026-11-14 (close views, a second WebGPU implementation), 2026-11-15 (the close views on WebGL2 and their comparison, the canvas picture check of the harness, the one-command run for a machine with a GPU) and 2026-11-16 (the real canvas captured on the software adapter, the replay of captured frames on the second implementation, negative controls of the harness, the scrub-purity lint, the timing harness). Code: `app/src/weather3d/gpu.mjs`, `app/src/weather3d/shaders-wgsl.mjs`, the host side in `app/src/fx-host.mjs`, one hook in `render/prototype/src/webgpu.mjs`. Register entry EG-W3D-G08 (the path used to compute state and draw nothing). **Everything below was run on Chrome's software WebGPU adapter (SwiftShader). Nothing has run on a real GPU, no real-GPU timing was taken, and none is claimed.** Real-hardware checks are listed in `BROWSER-VERIFICATION-LIST-WEATHER.md` section E.

## 1. What it draws

The same layers as the WebGL2 path (`weather3d/gl.mjs`), from the same inputs (the `WeatherTimeline` state, the fx3d frame, the prototype `Camera`), in the same order with the same blend states:

| Layer | WebGL2 | WebGPU |
|---|---|---|
| sky gradient, sun glow, twilight glow, stars, moon with phase, cloud layer, night floor on the sky | `WEATHER_FS` (GLSL), draw MUL then ADD | `WEATHER_WGSL` (WGSL), pipelines `weather3d-mul` and `weather3d-add` |
| undo of the prototype's baked fog, this layer's fog, wet ground and puddles, light of flashes and fires | same fragment code | same |
| smoke, muzzle flash, shell bursts, clods, dust, fire flames, fuse sparks, soft particles against the scene depth | `GLSL_VERT/FRAG` of fx3d, one instanced draw | `WGSL_RENDER` of fx3d (depth read patched), pipeline `fx3d-sprites`, one instanced draw |

The WGSL is a port statement for statement; it differs only where the API does (WebGPU depth is 0..1 so there is no `* 2 - 1`; the frame block is the prototype's bind group 0; the mode is a module constant, two modules; the hash is one function). `tests/weather3d-gpu.test.mjs` pins this: every numeric constant of the GLSL is in the WGSL and the other way round (the count differences are exactly the hash refactor and the clip conversion), the uniform block has the member order and offsets the packer writes, and `packWeather` writes exactly the values `gl.mjs` sends to the WebGL2 program (the real `gl.mjs` code runs against a recording stand-in for the GL context), for five scenes and 0, 3, 16 and 20 lights.

## 2. How it is wired

* `render/prototype/src/webgpu.mjs` calls `this.ext.after(enc, this)` between its scene pass and its particle and post passes (one line, null-guarded, absent from the prototype's own use; the WebGL2 renderer needs no such hook because its `ext.scene` runs inside the scene pass).
* `fx-host.mjs` chains `after` after whatever hook the renderer holds (the figures and structures use `scene` and `shadow`; they keep working in either order of attachment), switches the prototype's own sky and particle passes off (`R.o.flags.sky`, `R.o.flags.particles`) **only when the new pipelines built**, and restores them in `dispose()` or when a validation error names this layer (`gpu.failed`; the state is still computed).
* `GPUPasses.draw(enc, W, fr, cam, flags)` encodes ONE render pass: colour = the HDR target, `loadOp: 'load'`; depth = the scene depth attached read-only (`depthReadOnly: true`) and sampled in the same pass (a read-only attachment and a sampled binding are both read-only usages), so no depth copy is needed (WebGL2 blits the depth to a copy). Inside: group 0 = the prototype's frame block (dynamic offset 0), group 1 = this pass's uniforms and the depth view; two full-screen triangles (multiply: `dst * D`, add: `dst + A`, so `dst_final = dst * D + A` per channel, as on WebGL2), then one `draw(4, nSprites)` of the sprites (triangle strips, `depthCompare: 'less'`, no depth write).
* Bytes held (laptop tier, 12,288 event slots): about 1.24 MB (event storage 1.19 MB, cumulative counts 49 KB, wind history 2 KB, two uniform blocks). Resize: the bind groups hold the renderer's depth view and are rebuilt when it changes. `stats.passMs` carries a timestamp-query time of the pass where the device has the feature (software value here: not a GPU figure).
* Same inputs, same pixels: no `Math.random`, no clock in the path; the uploaded values are pure functions of (simulation time, camera, scenario choices).

## 3. Evidence, and what kind it is

All of it from `app/tests/weather3d-gpu.mjs` (headless Chrome 153, software WebGPU adapter `google / swiftshader`, 640 x 360, a 12,000-soldier placeholder world, tier `laptop`, 16 cases of `weather3d-gpu-cases.mjs`), `weather3d-gpu-compare.mjs` and `weather3d-gpu-theatre.mjs`; stored in `app/tests/results/weather3d-webgpu/` (summaries, comparison numbers, the 16 WebGPU pictures), read back by `weather3d-gpu-check.mjs` and pinned by a node test.

* **No WebGPU validation errors.** The three modules (`weather3d-mul`, `weather3d-add`, `fx3d-sprites`) and the optional compute module compile with no compiler message (not even a warning), as do the prototype's own eleven; the three render pipelines build; `uncapturederror` never fires; every case frame ran inside a validation error scope and none popped an error; the device was not lost before the harness destroyed it at the end; the same at the `phone` tier (4,096 event slots) and the `desktop` tier (16,384) for four effect cases each; a resize to 480 x 270 and back rebuilt the bind groups (3 builds) with no error and gave back the first picture byte for byte.
* **Pictures seen.** Read back from the frame's last target (section 4) and looked at: night sky with stars and cloud, the moon disc at 7 degrees of view with stars and cloud, dusk glow, dawn mist with the sun glow on the horizon, daytime clouds, wet ground with puddles reflecting the sky, men on wet ground, musketry and cannon smoke by day and night (the same frames carry the plan's shell bursts and ground strikes), flash light on the ground and the men at night, the Sherfy barn fire (inside its date window, drawn at the half intensity of a time-uncertain fire), road dust of a marching column (the same frame carries the dust of falls). Bursts, clods and fall dust were not picked out one by one.
* **Parity with WebGL2** (same time, same camera, both software): mean absolute difference per channel 0.33 to 0.46 of 255 over the 16 cases (p99 of the largest channel difference 1 to 2; at most 0.45 percent of pixels differ by more than 8 levels, 0.19 percent by more than 24, all along the far horizon where thin geometry rasterises differently). The prototype alone (`--fx=off`: its own sky and particles, no layer) differs between the two APIs by 0.36 to 0.43 in the four cases measured, so the layer adds no measurable difference of its own. Sprite counts are identical in every case (the same fx3d frame feeds both). Mean luminance of the frame agrees to 0.03 percent.
* **Scrub purity and reproducibility.** The same time and camera give byte-identical pictures: the case, the same case again at once, another case, the first case again (WebGPU and WebGL2); and two complete runs in separate browser launches an hour and a half apart gave byte-identical pictures in all 16 cases on WebGPU.
* **The optional GPU-cull compute shader** (`WGSL_COMPUTE`, not wired: both APIs draw the CPU-culled frame) compiled but did not build a pipeline under the default limits (`workgroup_size(1024)` against a limit of 256). It is now one workgroup of 256 threads with 72 events each (capacity 18,432, more than the largest budget's 16,384 + 64 flame slots) and builds; `fx3d.test.mjs` pins the capacity. Its results have not been compared with the CPU cull: open, see section 5.
* **The six close views (WebGPU run of 2026-11-14, software adapter; `close-webgpu-summary.json`, `close-webgpu/*.png`).** Shell burst, ground strike, fresh volley, dust at falls, the barn fire close and at night (2,523, 2,395, 2,689, 50, 2,260 and 534 sprites): no validation error in any case frame, no uncaptured error, no compiler message in the 15 modules the page built, the optional compute pipeline builds, three repeats gave byte-identical pictures, and the resize to 480 x 270 and back gave the first picture byte for byte. The six pictures were looked at: the strike and burst views are dominated by the batteries' soft smoke puffs (the stand-in plan puts smoke in front of the camera), so the clods, the burst flash and the fragments cannot be picked out in them; the volley view shows a row of musket-smoke clouds at 30 m against the haze; the fall view a low dust haze at the place where men fell; the fire views flames, a dense dark plume and, at night, the fire's light on the ground. **Parity of these six with WebGL2 (the WebGL2 run of 2026-11-15, same harness, software, 129 s: 0 errors, three purity repeats and the resize byte-identical; `close-webgl2-summary.json`, `close-webgl2/*.png`, `close-compare-summary.json`):** mean absolute difference 0.333 to 0.396 of 255 per channel over the six, p99 of the largest channel difference 1 in all six, at most 0.2 percent of the pixels over 8 levels and 0.06 percent over 24 (the dust-at-falls view, along the far horizon where thin geometry rasterises differently, as in the 16 cases), identical sprite counts in all six (2,523, 2,395, 2,689, 50, 2,260 and 534), mean luminance equal to 0.01 percent. The six comparison montages (WebGL2 | WebGPU | difference x4) were looked at: the same smoke puffs, the same sparks and flames, the same dust at the horizon and the same fire light at night on both; the difference pictures are black but for thin lines along the horizon. The run checker is clean for both APIs. So the effect classes draw on WebGPU and equal WebGL2 to the figures above, on software adapters.
* **A second WebGPU implementation (2026-11-14; `second-implementation-build.json`; software only).** The same WGSL, the prototype's real group 0 layout (twelve bindings) and this layer's two groups, the same blend and depth state, through wgpu-native 0.33 (Python package `wgpu`: the naga compiler and wgpu-core's own validation, the implementation behind Firefox's WebGPU) on SwiftShader's Vulkan, run by `tests/weather3d-gpu-replay.py`: the three modules and the optional compute module compile with no message, the four pipelines build, and five negative controls are refused by the same implementation (a type error, an unknown member, the scene depth declared as a float texture, the uniform block hidden from the fragment stage, and the same depth texture attached for writing and sampled in one pass), so the positive results are not vacuous. The pass encoding the layer uses (depth attached read-only AND sampled in one pass; colour loaded; group 0 at a dynamic offset) is accepted by that implementation, on arbitrary numbers (`selftest`). The other WGSL of the renderer (the prototype's eleven modules, the crowd's, the structures'; `tests/weather3d-gpu-wgsl-other.mjs`, shader constants as in `webgpu.mjs`, imposter atlas sizes stand-ins) also compiles there: 13 of 13, module level only (nothing about their pipelines or pictures). What this is not: a GPU, a GPU vendor's compiler, or a Firefox run.
* **The real canvas of a WebGPU page was captured on this machine's software adapter (2026-11-16; `xvfb-probe/`, `H5-page.png`, `H5-xscreen.png`; looked at).** Headed Chrome 153 under a virtual X server (`xvfb-run -a -s "-screen 0 1280x720x24"`) with the harness's flags plus `--use-vulkan=swiftshader --disable-vulkan-surface` (flag set H5 of `tests/weather3d-gpu-xvfb-probe.mjs`): the device stays alive, `drawImage` of the canvas reads (255, 128, 0, 255), `page.screenshot` shows the whole orange 128 x 128 canvas, and so does a capture of the X screen. The other four headed sets (H1 the harness flags, H2 plus software compositing, H3 the `--use-webgpu-adapter=swiftshader` form, H4 plus `--ozone-platform=x11 --disable-gpu-sandbox`) lose the device ("Device was destroyed") and show black, as the headless sets of section 4 did. So the statement "no flag set can capture the real canvas here" is true only for headless Chrome and those four headed sets. **The harness on that canvas (`--xvfb-canvas`, four cases, `tmp` run of 2026-11-16 03:03 UTC, summary read by the run checker): for every case the compositor's picture of the canvas (`page.screenshot`) equals the read-back of the same frame, mean absolute difference 0 levels (maximum 0); the read-back from the real swapchain texture works; the pictures read back from the real canvas of three of the four cases (stars, day clouds, the Sherfy barn fire) are byte-identical to the stand-in pictures stored on 2026-11-13** (the fourth, the smoke case, differed because a case's effect state then depended on the case drawn before it when the two shared their minute: found and fixed in the harness the same day, see "Found" below). The fire and the stars pictures were looked at. This is still a software adapter: it shows that the canvas path, the compositor and the read-back agree on this machine, not what a GPU or its compositor does.
* **12 frames of the layer's pass, captured on Chrome and replayed on the second WebGPU implementation (2026-11-16; `capture-replay-report.json`, `capture-summary.json`).** `tests/weather3d-gpu-capture.mjs` (12 of the 16 cases, no validation error) wrote everything the pass reads in each frame (the prototype's frame block, the layer's two uniform blocks, the effect events with their cumulative sums and the wind history, the scene depth) and the colour target before and after the pass; `tests/weather3d-gpu-replay.py` ran that pass on wgpu-native 0.33 (the naga compiler and wgpu-core's validation) on SwiftShader's Vulkan and compared: the three modules and the optional compute module compile with no message, the four pipelines build, the five negative controls are refused, and in all 12 frames the colour target after the pass equals Chrome's: worst maximum absolute difference 0.000488 in HDR units (the half-float rounding scale), mean absolute difference 2.2e-9 or less, 99.997 to 100 percent of the values bit-identical, every value finite, 100 percent of the pixels changed by the pass (so the comparison is not vacuous), 0 to 14,951 sprites. Both implementations ran on the same software Vulkan driver, so this shows that the WGSL means the same to two compilers, not that a GPU computes it the same way.
* **Negative controls of the harness (2026-11-16; `tests/weather3d-gpu-negctl.mjs`, judged by `checkNegativeControl`).** "No validation error, no uncaptured error, no compiler message" is only worth something when the machinery that reports it sees errors. At the end of a WebGPU run the page makes errors on purpose and the run says whether each path saw them: an error scope hands back a made-on-purpose validation error and stays silent on a valid call; a shader module with a type error carries a compiler error, is caught by a scope and is recorded by the harness hook; an unscoped error arrives as an `uncapturederror` event and is recorded; an asynchronous pipeline with a missing entry point is refused while the same one with the entry point builds; a whole frame with a bind group of the wrong layout reports a validation error through the SAME per-case scope as every case, the frames before and after are clean and the layer is not stopped. What the controls make is marked and taken out of the run's own error lists. **First run in a browser (the real-canvas run above): four of the five controls were seen (the whole-frame control caught "Bind group layout [weather3d.bglW] of pipeline layout [weather3d.layout] does not match layout [harness negative control layout]"); the uncaptured-error control was NOT seen, and that is a finding: Chrome delivers an unscoped error when the GPU process next answers, not when the call is made; the event arrived tens of seconds later (the hook recorded it after the control had given up and the control's cleanup removed it), so the control now makes a round trip (`queue.onSubmittedWorkDone`) after the invalid call, and `WG.diag()` reads the error lists after a round trip too. The corrected controls have run in no browser yet (node tests with a stand-in device that delivers errors lazily, as Chrome does, and one that never does; the browser run is queued, section 5).**
* **Scrub purity of the draw path, in node (2026-11-16; `tests/weather3d-determinism-lint.mjs`, `weather3d-determinism.test.mjs`, two tests in `weather3d-gpu.test.mjs`).** The same simulation time and camera must give the same pixels, so nothing that decides what is uploaded may read a clock or a random source. A syntax-tree lint (acorn, not text) reads all 20 modules of `src/weather3d`, `src/fx3d` and `src/fx-host.mjs` (a new file in those folders is covered by being there) and finds no `Math.random`, `Date.now`, `new Date()`, `performance`, `crypto`, `hrtime`, `eval` or `Function`, however spelled or aliased; its own tests plant each kind of defect (also in a copy of a real file) and each must be found under its rule, and the constructs it allows on purpose (bounded `setTimeout` waits, dates built from their inputs, `typeof`, GPU-time statistics) are not reported. It is not scope aware: a parameter named like a global and used is reported (rename it). The behavioural half replaces `Math.random`, `Date.now`, `new Date()` and `performance.now` by counters and runs the weather state, a real effects frame, both uniform packers and the encoded pass: the counters stay at zero, a scrub away (400 s) and back to the same two times gives the same events, cumulative sums, wind history and lights, and the same inputs give identical uploads and the same encoded pass; a control shows that the counters count.
* **Found while building the harness.** (1) The canvas cannot be used on this machine's software adapter (section 4). (2) A first version of the harness hook asked a shader module for its compiler messages a second time while the layer's own set-up was asking for them; in that state the layer's set-up (and with it the shell's entry on WebGPU) stalled with the browser idle. The stalls stopped when the hook stopped asking twice; the cause inside the browser was not investigated. Because a stall on the device must never hold the shell, every wait of the layer's set-up on the device is now bounded (60 s for the pipelines, 10 s for the validation scope, 3 s for the compiler messages; a node test with a device that never answers) and what does not arrive is reported as not built or unknown. (3) The one 404 the first runs showed was the browser's own favicon request. **Found on 2026-11-16:** (4) a case's effect state depended on the case drawn before it when the two shared their minute (the stand-in plan changes its flags between cases without the effects host knowing, and the host replays only after a time jump): `smoke-jul3-1400` drew 163 sprites after `day-clouds-jul3-1400` of the same minute and 6,379 after any other case. In the shell the plan is the crowd's and does not change under the host, so the shell is not affected; the page harness now replays from the case's time whenever the plan's flags or anchor change (`WG.render`, `WG.capture`), which leaves the default list of 16 cases and the list of six close views unchanged (no two neighbours in them share a minute with different plans) and makes a subset of cases give the pictures of the full run (the queued runs check the 16 pictures byte for byte against the stored ones). (5) The error lists of the page (`WG.diag`) were read without a round trip to the GPU process; they are now read after one.

## 4. Why the pictures are read back from a texture of our own

**Update 2026-11-16: in headless Chrome and in four of five headed flag sets the real canvas cannot be used on this machine's software adapter; in one headed flag set it can (section 3, first new bullet; the flags are `XVFB_CANVAS_ARGS` in `weather3d-gpu-lib.mjs`, the shortcut is `--xvfb-canvas` of the drivers, run under `xvfb-run`). The pictures of sections 3 and 5 are still read back from a texture of our own because that works everywhere; the real canvas is the second way, for the checks of presentation.** On this machine's software adapter in headless Chrome the real canvas cannot be used. Probed one operation per page load (`weather3d-gpu-swapchain.html`, summary `swapchain`): rendering to an own texture and reading it back works; configuring the canvas leaves the device alive; `page.screenshot` times out after 20 s in all of these page loads, with a canvas or without one, and returns a white page only after the device was lost; drawing into the canvas texture for a while destroys the device (`lost: destroyed`); copying out of the canvas texture ends with "A valid external Instance reference no longer exists". So the harness installs `HOOKS` (`weather3d-gpu-lib.mjs`) before any page script: `configure()` is not passed on and `getCurrentTexture()` returns an ordinary texture of the same size and format with `COPY_SRC`. The renderer records exactly the commands it records for a canvas; only the target of its last pass is not the canvas. What this cannot show: presentation of the canvas, the page compositor, colour management of the canvas, and anything about a real swapchain. `--real-canvas` uses the real canvas and only adds `COPY_SRC` to its configuration, for a machine with a GPU (not run here). Specs that want a WebGPU frame on a software machine can use `HOOKS` and read `R.ctx.getCurrentTexture()` in the frame's own task.

**Six other Chrome flag sets, tried in the run of the evening of 2026-11-13 (UTC)** (`app/tests/results/weather3d-webgpu/canvas-probe-flags.json`; one browser launch per set, a 64 x 64 canvas cleared orange through the real swapchain texture for 20 frames, then `page.screenshot` with a 25 s limit). None of them showed the canvas: (A) the harness's own flags: the screenshot times out and the device is destroyed; (B) without the `Vulkan` feature, `--use-webgpu-adapter=swiftshader`: a 165-byte white picture and "A valid external Instance reference no longer exists"; (C) B plus `--disable-gpu-compositing`: a black picture, the same message; (D) B plus `--in-process-gpu`: the browser does not start; (E) B with `WebGPUService` off: a white picture, device destroyed; (F) `--use-vulkan=swiftshader --disable-vulkan-surface`: the screenshot times out, the device stays alive. A seventh set (G, software compositing and an in-process GPU) hung for about five minutes with no browser process and was stopped by hand, and an eighth (H) was never started. So on this machine's software adapter there is no flag set among those tried with which the real canvas can be captured, and the read-back of a texture of our own stays the only way to see a WebGPU frame here. A further probe of other read paths of a configured canvas (`drawImage` of the canvas into a 2D canvas, `toBlob`, `toDataURL`, `createImageBitmap`, an `OffscreenCanvas` with `transferToImageBitmap` and `convertToBlob`, on Chrome and on the headless shell) is written and queued behind the machine lock; it has not been run, so none of those paths is claimed. **2026-11-15, run on 2026-11-16 (results above and in `xvfb-probe/`):** none of the flag sets above ran Chrome HEADED. `tests/weather3d-gpu-xvfb-probe.mjs` (driver `weather3d-gpu-xvfb-probe.sh`) tries five sets headed under a virtual X server (`xvfb-run`; set H1 is the harness's own flags, H2 adds software compositing, H3 the `--use-webgpu-adapter=swiftshader` form, H4 the X11 platform without the GPU sandbox, H5 the Vulkan-surface-off form): a 128 x 128 canvas cleared orange for 30 frames, then `page.screenshot`, an X screen capture (`import -window root`) and a `drawImage` of the canvas, each recorded with the picture. It ran on 2026-11-16 in a few seconds per set: set H5 shows the canvas, H1 to H4 do not (section 3).

## 5. What is not done or not known (nothing hidden)

* **Any real GPU.** Intel Arc, NVIDIA, AMD, Apple (Chrome, Safari), a phone: compile of the back-end, the picture, the cost (section E of the verification list). The read-only depth attachment that is also sampled, the `r32float` height texture sampled with a filtering sampler (needs `float32-filterable`, which the prototype requests when the adapter has it; the prototype's own bind group 0 declares the same texture and sampler, so its passes depend on the same feature), `rgba16float` blending: all standard WebGPU, none seen on hardware.
* **Cost.** `stats.passMs` exists; the number measured here is a software figure. The `fx3d` governor is not fed from it (the pass time includes the weather draws; feeding the sprite governor with it would mix the two).
* **GPU cull.** `WGSL_COMPUTE` builds but is not wired (indirect draws, the events with their full-LOD counts, a camera block per frame) and has not been compared with the CPU cull; the CPU cull stays the path on both APIs, so no capability is missing relative to WebGL2.
* **Done 2026-11-15: (a) the six close views on WebGL2 and their comparison with the WebGPU pictures (section 3). Done 2026-11-16 (job A of `tmp/bt-renderer-wgpu/`, which ran in minutes once the machine lock let it in): (b) the canvas-picture code path of the harness on WebGL2 (two cases, page.screenshot against the read-back: mean absolute difference 0); (c) the real canvas in five headed flag sets under Xvfb (one shows it, section 3); (d) the harness on that canvas, four cases; (e) the capture of twelve frames and its replay on the second implementation (section 3).**
* **Queued behind the machine lock and NOT run when this was written (the lock was held back by two waiting timing jobs and about thirty other jobs; scripts and logs in `tmp/bt-renderer-wgpu/`, resumable: `B.log`, `C.log`, `E.log`):** job C: the 16 cases on both APIs on the present tree with the corrected negative controls, the comparison and the run check (`--require-negative-control`), then the timing harness on both APIs as a functional run (small, 20 frames: the numbers of a software adapter mean nothing; it shows only that `WG.timing`, the driver and the checker work in a browser); job E: the 16 cases on the real canvas under Xvfb (`--xvfb-canvas`: the compositor picture of every case kept as `<case>-canvas.png`, purity and the resize on the real canvas, which no run has done) and the shell on the real canvas; job B: the shell (placeholder history layer, every extension module on) on both APIs at 640 x 360 and the comparison. **Until they have run, nothing is claimed about: the corrected uncaptured-error control, the timing harness in a browser, the 16 pictures on the present tree, the resize and the purity repeats on the real canvas, the shell on the present tree on WebGPU.** Not queued, to keep the lock free: the shell with the real crowd of about 127,000 figures on both APIs (`weather3d-gpu-theatre.mjs ... --real`, an hour or more; the crowd's own WebGPU item is open) and the other read paths of a configured canvas (`toBlob`, `toDataURL`, `createImageBitmap`, `OffscreenCanvas`; script written, section 4; `drawImage` was probed with the flag sets and works in set H5). Each is a software-adapter result at best; none changes the real-GPU items.
* **Not in either path:** cloud shadows on the ground, rain streaks (the shell's 2D rain canvas remains), shadows of flash lights (W-D2 of the list).
* **The shell** (theatre.mjs ribbon, config.mjs note, the tutorial, the README line about the hook points) still says the weather and effects are not drawn on WebGPU: request note `GOVERNANCE/horde/requests/bt-renderer-webgpu-weather-shell-text.md`. The default API stays WebGL2 (DD-27) until the real-GPU checks and the crowd's WebGPU item pass.

The timing harness (rows W-E4, W-C1, W-C2 of the verification list; written 2026-11-16, node-tested, its software-adapter run is listed in section 3): `node docs/battle-theatre/app/tests/weather3d-gpu-timing.mjs <out> <webgpu|webgl2> [--w=1920] [--h=1080] [--frames=600] [--warm=120] [--rounds=2] [--tier=desktop] [--soldiers=12000] [--dense=12] [--modes=both,off,weather,fx] [--scenarios=quiet,cannonade] [--real-gpu [--headed]]` (build machine: `tools/horde/bench.sh --timing node ...`, alone; a figure from the build machine is a software figure and the report says so first). It runs the harness page for each of four modes of the layer (both passes; neither; the weather pass alone; the sprite pass alone; the prototype's own sky and particles are off in all four, so `off` is the baseline) in two scenarios (the 14:00 clouds view of the 16 cases; the 14:00 smoke view with the stand-in plan multiplied by `dense`: 72 guns and 720 men at the default 12, about 9,000 events in a 61 s replay window), `rounds` times with the order of the modes reversed on every other round. Per frame, with the simulation advancing a 60th of a second as in the shell at speed 1: the CPU time of `fxHost.update`, of the frame's encoding, the time until the frame's GPU work is complete (`queue.onSubmittedWorkDone`, WebGL2 `gl.finish`: throughput, not paced by the display, because the canvas is the harness's stand-in texture), the sprites, and on WebGPU the layer's own GPU pass time from the timestamp queries. `summary.json` (every series), `report.md` (per scenario the four modes, the layer's cost as the difference of the medians, the pass time, the nanoseconds per sprite; the desktop effects budget of 4 ms is printed beside them and not applied). The checks (`weather3d-gpu-timing-lib.mjs checkTiming`) name what makes the figures unusable (an error, a validation message, a device loss, a missing series, a cannonade with no sprites, an adapter that is not the hardware asked for), never a slow figure.

Options: `--no-negctl` (leave out the negative controls of the harness, section 3: they run once at the end of a WebGPU run), `--fx=off` (the prototype alone), `--extra` (the six close views instead of the 16 cases), `--real-canvas` (no stand-in for the canvas texture), `--canvas-shot` (after each case, `page.screenshot` of the page against the read-back of the same frame: mean absolute difference per channel, p99 and the shares over 8 and 24 levels, or the error; on by default with `--real-canvas` and `--real-gpu`, off with `--no-screenshot`; the run checker makes a failed picture, or one more than `CANVAS_SHOT_LIMIT` = 4 levels from the read-back, a problem: a harness value, not a project gate), `--real-gpu [--headed]` (a run on a machine with a GPU: Chrome without the software-rasteriser flags and the real canvas; the run checker refuses to call it a real-GPU run when the recorded adapter is a software one), `--no-repeat`, `--no-screenshot`, `--w`, `--h`, `--soldiers`, `--tier`. On a machine with a real GPU run the first two commands with `--real-gpu` (and the `--extra` pair) and compare; the checks to write down are in `BROWSER-VERIFICATION-LIST-WEATHER.md` section E. **Or run the whole procedure with one command (the step for the owner, see section 7):** `node docs/battle-theatre/app/tests/weather3d-gpu-realrun.mjs <outDir> [--headed] [--w=1920] [--h=1080] [--real-crowd]`.

## 7. The step for the owner: the real-GPU run in one command

Owner-only, because the build machine has no GPU and nothing in sections 3 to 5 is a real-GPU result. On a machine with a GPU (the README's measurements name an NVIDIA RTX PRO 1000 Blackwell laptop with Chrome 155), from the repository root, with the repository's `node_modules` (Playwright) as for the other browser tests:

```
node docs/battle-theatre/app/tests/weather3d-gpu-realrun.mjs C:\temp\w3d-real --headed
```

(`--headed` where headless Chrome has no GPU access; add `--real-crowd` for the shell with the crowd of figures, which is long; for the phone-size window of W-E3 run it a second time into another folder with `--w=390 --h=844 --skip-close`; `--dry` prints the plan; no flag needs the machine lock, which exists only on the build machine.) It runs, one step after the other, each in its own process with its output in `<outDir>/logs/`: the 16 cases on WebGPU and WebGL2 at 1920 x 1080 with the real canvas (and the compositor's picture of the canvas compared with the read-back of each frame, W-E7), the comparison with a montage per case, **the timing harness on both (600 frames after 120 warm-up frames at 1920 x 1080, desktop tier, a quiet sky and a dense cannonade, the layer's passes on, off and each alone, two rounds: the pass time from the timestamp queries and the frame time, section 6)**, the six close views on both and their comparison, the shell on both and their comparison; then `REAL-GPU-RESULT.md` and `.json`: per row W-E1 to W-E9 what the machine could check (run checker, parity numbers, the adapters, the pass time of one frame per case, the 600-frame timing figures, the canvas pictures) and what is still owed. **The result starts with "NOT A REAL-GPU RESULT" when any run recorded a software adapter or was not a `--real-gpu` run**, so a run on the wrong machine cannot pass. No script judges a picture: the rows of the verification list are ticked by a person who has LOOKED at the montages (`<outDir>/main/compare/*.png`, `<outDir>/close/compare/*.png`, `<outDir>/shell/theatre-compare/*.png`). The rows this command cannot answer are named in its result as owed: Safari and Firefox (W-E6), a device without `float32-filterable` (W-E5), other vendors (run the command on each), the 600-frame timing split inside the shell on the real crowd (W-E4: the command times the layer on a stand-in world of 12,000 soldiers with no crowd) and the wiring of the GPU cull (W-E8). `--skip-timing` leaves the timing steps out. Send the folder `<outDir>` (or only `REAL-GPU-RESULT.md` and the three `compare` folders) back; do not edit the files. Nothing in it is deployed or published by this command.
