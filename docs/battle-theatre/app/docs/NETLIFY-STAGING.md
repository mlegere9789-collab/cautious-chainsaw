## Build
- `node tools/bt/verify_staging.mjs --pack` is the whole honest run: it copies the tree to a snapshot (so that nobody's edit moves the target during the run), packs the snapshot (the zip and its `.sha256` go to `deliver/`, the dist to `tmp/bt-spec/verify/work/dist` so that a job that is serving `deliver/bt-staging/dist` is never disturbed), checks the dist and the zip, walks the packed site and the snapshot in a browser and compares them. Only a build that passes every check refreshes `deliver/bt-staging/dist`; `deliver/bt-staging/LAST-VERIFY.txt` says in every case what the last run found. On the shared machine start it through the lock: `tools/horde/bench.sh node tools/bt/verify_staging.mjs --pack --json tmp/bt-spec/verify/<name>.json` (a software frame takes seconds; the run takes about an hour).
- `node tools/bt/pack_theatre.mjs` is only the build (`--no-zip` for the dist alone, `--out`, `--zip-dir`). It exits 2 and names the lines when the copy audit finds anything; the zip of such a build carries `-AUDIT-HITS-<n>` in its name. The zips of earlier builds that failed the audit are removed by the next pack; a clean zip is never removed.
- The build is deterministic: the same sources give the same bytes, the same zip and the same 8-character id. The id is shown in the lower-left corner of the page ("Battle Theatre staging build <id>") and is in `MANIFEST.json` (size and SHA-256 of every file). `deliver/` is not committed.
- Self-tests: `node --test tests/bt-pack/pack.test.mjs tests/bt-pack/verify.test.mjs` (the packer on the real tree and on a made-up one that holds every kind of load; the checks of the verification on made-up folders and request logs). `BT_PACK_NO_BROWSER=1` skips the one test that starts a browser; otherwise run them through the machine lock.

## What the owner does
1. In Netlify, add a new site by dropping a folder or zip (labels on Netlify screens are from memory; if one differs, stop and ask). Drop the zip, or the unzipped `dist` folder, onto a **new throwaway site**, not the production site.
2. Open the address Netlify gives. The root page forwards to `/app/index.html`. Press the enter button on the landing page.
3. Send the address back so the checks can be run against it. Delete the throwaway site when done.

The site sends `X-Robots-Tag: noindex, nofollow` (and a robots meta tag) so search engines ignore it. The "Return to the map" link goes to the staging root, not to the main map.

## What is in the zip
The shell (`app/`: the page, its style sheet, every module of `app/src/` including the added layers in `app/src/ext/`, and the data files the modules load: `app/data/*.json`, `audio3d/`, `anim3d/`, `fx3d/` and two of the figures' files) and exactly the siblings it requests at runtime: the prototype renderers and terrain (`render/prototype/`), `sim/`, `GOVERNANCE/` (timeline, register index reduced to the entry ids, conflicts), `environment/`, `history/`, `structures/`, `kit/`. The folder layout is kept so every relative URL works from the site root. The numbers of the current build are in the block at the top.

How the files are found (`tools/bt/pack_theatre.mjs`, header comment): the pages and their style sheets; the import graph of the modules (static imports, `import('literal')`, bare names through the import map, and computed imports with a literal folder prefix: `import('./ext/' + path)` takes the folder, and `src/ext/index.mjs` says which modules the page loads); every file address in the code (`URLS.<key> + 'file'`, the same through `ctx.urls.<key>` in an added layer, template strings with a literal prefix, `new URL('relative', import.meta.url)`, `fetch('literal')`, workers); a static section beside the shell (`app/roster`, when it exists: every page, script, style sheet and the files its index lists) and an explicit include list for the data the features load through a base path the scan cannot follow. A real run then confirms the result (next section). Left out: tests, screenshots, notes, tools, and the files of the figures' data folder that no feature loads.

Files are not renamed with hashes (the modules import each other by relative path); `_headers` sets `Cache-Control: max-age=0, must-revalidate`, so the browser revalidates against Netlify's content ETag and unchanged files return 304. No COOP/COEP headers: the shell uses no SharedArrayBuffer.

## How the build is checked
`tools/bt/verify_staging.mjs` (the numbers of the last run are in the report it writes with `--json`):

1. **Static**: the dist equals its `MANIFEST.json` byte for byte and has no stray file; the zip holds exactly the dist (names, sizes, CRC-32), has no comment, its `.sha256` file is right, `unzip -t` passes, and its name carries the build id; every relative import, style-sheet address, link and import-map target of the dist exists; no README, note, source map, log or backup ships; the root page forwards to `/app/index.html`; and the data side of the theatre's start runs in node from the dist alone (timeline, conflicts, sky tables, bookmarks, terrain, the history data, the real history layer, the structure inputs, with `fetch` answering 404 for a file the dist lacks), which finds a missing data file in a second and without a browser.
2. **The packed dist is served the way Netlify serves it** (its `_headers` applied: content types, `nosniff`) and walked in a browser (software WebGL2, one at a time): enter the theatre with the figures, effects and structures on; wait for the added layers to settle; start the sound (what a click does); 3 July 13:30; fly to a unit; play at 2x and at 60x; 4 July 15:00 (rain); open every drawer; select a unit; switch every added layer on, open every added panel, fly to a tour stop, switch them off; press Back. Then every page of a static section is visited, its links followed and its controls pressed (when the section exists).
3. **The same walk is made against the snapshot of the source tree**, and the two request logs are compared.
4. **The check fails** when any request to the packed site does not answer 2xx (zero 404s), when a URL the source run loaded is not in the dist (nothing missing), when a console or page error appears only in the packed site, when a step that passes at the source fails in the dist, when the sound does not start, when an added layer is in another state than at the source, when a section page does not load, or when the copy audit finds anything.

What a run of this kind cannot show is printed with every verdict ("NOT RUN here"): a real GPU (no frame time, long task or input delay is measured; software rendering shows pictures, not speed), the WebGPU picture, hearing the sound, other visits (`?history=stub`, `?ext=off`, `?crowd=off`, a phone-sized page, a second entry after Back), other browsers and real phones. Files that ship because the trace found a reference but that this walk never requested are listed in the report (`shippedNeverRequested`); they are covered by the trace and the static checks, not by the real run.
