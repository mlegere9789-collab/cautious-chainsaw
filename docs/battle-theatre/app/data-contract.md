# History-layer contract (version 1.0; additions up to 1.8 below)

The page shell never reads history from files of its own. It asks a **history layer** for six things, in the shapes below. There are two layers: the real one,
`src/history/real.mjs` (the default; see the 1.1 section at the end for what it added), and the placeholder `src/history/stub.mjs` (`?history=stub`; every datum is a *Modelled placeholder*).
The shapes are enforced by `src/history/contract.mjs` (`validateLayer`, `validateUnits`, `validateArrivals`, `validateEvents`, `validateKit`), which `tests/unit.test.mjs` runs on the stub and which the shell runs on whatever layer it is given before it starts.

## Conventions

| Thing | Rule |
|---|---|
| Time | **minutes since 1863-06-01 00:00 local mean time (LMT = UT + longitude/15 h)**, the unit of `GOVERNANCE/timeline_windows.jsonl` (`default`, `earliest`, `latest`). Fractions allowed. The sim event cache receives seconds (`minutes * 60`). |
| Place | WGS84 `{ "lng": -77.2345, "lat": 39.8112 }`. The shell converts to the terrain frame (x east, z south, metres). Never send terrain-frame numbers. |
| Uncertainty | every position carries `sigma_m`, a radius in metres that holds the true place with the stated tier's confidence. It is drawn as a ring and shown in the card. |
| Tier | one of `"documented"`, `"inferred"`, `"plausible-procedural"`, `"open gap"` (PDF Part E, Evidence-Gap Register). |
| Source keys | strings that resolve in `sources` (below). A tier of `documented` needs at least one source whose `kind` is not `lead`. |
| Ranges | strengths and casualties are ranges with a declared basis, never one number (C-046, C-047). |
| Scenario | every method that depends on a source conflict receives the scenario object (see **Scenarios**). |

## 1. `units` (static roster) &mdash; `layer.units: Unit[]`

```json
{
  "id": "US-I-1-2-20ME",
  "name": "20th Maine Infantry",
  "short": "20 ME",
  "side": "union",
  "arm": "infantry",
  "parent": "US-I-1-2",
  "level": "regiment",
  "strength": { "min": 358, "max": 386, "basis": "OR vol. 27 pt. 1, return of 30 Jun; range kept (C-047)", "tier": "documented", "sources": ["OR27-1"] },
  "formation": { "kind": "line", "ranks": 2, "facing_default_deg": null },
  "kit": "KIT-US-20ME-1863-07",
  "tier": "documented",
  "sources": ["OR27-1", "BUSEY-MARTIN"],
  "register": null,
  "notes": ""
}
```

`side` is `union|confederate`; `arm` is `infantry|cavalry|artillery|headquarters|staff|medical|train`; `formation.kind` is `line|column_fours|column_mass|skirmish_line|battery|mounted_column|mounted_line`. `strength.min <= strength.max`, both integers. The shell instances one figure per man; where inside the range the drawn count sits is a scenario decision (`sim/loss_solver.mjs: pickCount`), never an average chosen silently, and the card always shows the range. `register` is an Evidence-Gap Register id (`EG-0001`) when the tier is not `documented`.

## 2. `arrivals(scenario)` &mdash; `Arrival[]`, one per unit

```json
{
  "unit": "US-I-1-2-20ME",
  "earliest": 54390,
  "default": 54401,
  "latest": 54470,
  "entry": { "lng": -77.2631, "lat": 39.8402, "sigma_m": 150 },
  "tier": "inferred",
  "sources": ["OR27-1"],
  "conflict": "C-004",
  "note": ""
}
```

`earliest <= default <= latest` (minutes). **`earliest` is the hard gate (Q04):** no entity of the unit exists before it. The unit appears at `entry`, which must lie off the loaded ground (the shell parks it 60 m beyond the edge plus its radius), and **marches** in: the route is the `path` event below. `conflict` names the source conflict (`GOVERNANCE/conflict_register.json`, `C-0xx`) whose chosen value produced these times, or `null`.

## 3. `events(scenario)` &mdash; the state schedule, time ordered

The sim event cache replays these. Event types:

| `type` | fields | meaning |
|---|---|---|
| `enter` | `at: {lng,lat}` | the unit exists from `t`. Must satisfy `t >= arrival.earliest`; otherwise the cache **refuses** the event and lists it (Q04). |
| `path` | `wp: [{t,lng,lat,sigma_m}, ...]` (>= 2, `wp[0].t == t`, non-decreasing) | **positions with uncertainty.** Linear between waypoints, held after the last. Several `path` events chain a movement. |
| `activity` | `activity`, `heading_deg?` | what the unit does from `t` (table below). `heading_deg` is a true bearing, 0 = north clockwise; the shell turns the formation smoothly (25 s) and never snaps. |
| `state` | `agent`, `fate`, `strength_now: {min,max}`, `killed`, `wounded`, `missing`: `{min,max}`, `down` | contract 1.3: **one man leaves the line** (`agent` = the index of his figure inside the unit, `fate` killed, wounded or missing) and the unit's running counts as RANGES. The stage turns a killed or wounded man into a fall in the renderer's soldier table; a missing man is counted, not animated. See "Contract 1.3". |
| `formation` | `formation`, `duration_s?`, `clause?` | contract 1.3: the unit changes formation from `t` (a printed “deploys”); the stage blends its figures between the two slot layouts over `duration_s` (default 90 s) with a smoothstep, never a snap. |
| `leave` | | the unit is gone from `t`. |

All events also carry `tier` and `sources`. Activities and what the renderer shows:

`march`, `double_quick`, `halt`, `stand`, `rest`, `fire`, `serve_guns` (battery crews), `gallop`, `build_works`, `camp`.
(`contract.mjs: ACTIVITIES` maps each to a clip for foot and mounted figures.)

## 4. Kit manifests &mdash; `kit(unitId, t) -> Manifest`

```json
{
  "id": "KIT-US-20ME-1863-07", "unit": "US-I-1-2-20ME", "valid_from": 54000, "valid_to": 56000,
  "items": [
    { "category": "Headgear", "item": "kepi, M1858 forage cap", "tier": "inferred", "sources": ["REPRO-STD"], "valid_from": 54000, "valid_to": 56000 },
    { "category": "Shoulder arm", "item": "rifle-musket, 0.58", "tier": "documented", "sources": ["OR27-1"], "valid_from": null, "valid_to": null }
  ],
  "validator": { "rule": "PDF B.6.12 kit validator", "passed": true, "note": "" }
}
```

`validator.passed` is `true|false|null` (null = not run, with a `note`). Every item must be valid on its date and for its unit (Q03); the validator, not the shell, decides.

## 5. `sources` &mdash; `{ [key]: Source }`

```json
{ "key": "OR27-1", "label": "Official Records vol. 27 pt. 1", "kind": "primary", "weak": false, "citation": "..." }
```

`kind` is `primary|secondary|lead|register|placeholder`. The card prints key, label and citation, and links `register` entries to `GOVERNANCE/register/<id>.md`.

## 6. `objects` &mdash; structures and works

```json
{ "id": "OBJ-ANGLE-WALL", "name": "stone wall at the Angle", "kind": "fence", "pre_existing": true, "built": null, "tier": "documented", "sources": [], "line": [{"lng":..,"lat":..}, {"lng":..,"lat":..}] }
{ "id": "OBJ-CULPS-WORK", "name": "breastwork", "kind": "earthwork", "pre_existing": false, "built": { "from": 52000, "to": 52220 }, "tier": "inferred", "sources": [], "line": [ ... ] }
```

A pre-existing feature is **never** given a construction animation (PDF B.7.3). A built work does not exist before `built.from` and is drawn growing to `built.to`. `layer.objectProgress(obj, t)` returns 0..1.

## Scenarios

The Sources panel lets the viewer choose a value for each conflict (C-001..C-047 and the weather file's `CF-*`). The shell passes

```json
{ "id": "pdf-recommended", "choices": { "C-004": "v0" }, "optionText": { "C-004": "22:30 Jul 1" } }
```

to `arrivals`, `events` and (for weather) its own environment code. `choices` is empty for the default, **"PDF recommended, pending owner"**; `optionText[id]` is the printed text of the chosen option (`recommended` or one of the printed values), so the layer can read the clock time or phrase. A layer must honour every `choices` entry it declares itself aware of (`meta.scenarioAware`) and must not silently pick among values.

## What the layer returns, in one object

```js
{
  meta:    { id, contract: '1.0', stub: false, label, scenarioAware: true, note },
  units:   Unit[],
  sources: { [key]: Source },
  objects: Obj[],
  arrivals(scenario) -> Arrival[],
  events(scenario)   -> Event[],
  both(scenario)     -> { arrivals, events },      // one call, one scenario resolution (used by the shell)
  kit(unitId, t)     -> Manifest,
  objectProgress(obj, t) -> number,
}
```

The stub additionally returns `binding` (`unit id` to the prototype crowd's unit index) because its renderer world is the prototype's placeholder crowd. A real layer does not need it: the shell builds the renderer world from `units` with `src/world-from-units.mjs` (strength and formation of each unit; the unit's place comes from `layer.slotOf`).

## Contract 1.1: what the real layer needed (additions; version 1.0 shapes are unchanged)

`src/history/real.mjs` is the first real layer. Four things in 1.0 assumed a placeholder world, so the contract grew; `contract.mjs` validates both forms and `tests/unit.test.mjs` and `tests/history.test.mjs` run them.

1. **A strength may have no figure.** The PDF prints strengths only for 13 corps rows and 8 brigades. For every regiment, battalion and battery with no figure the layer gives `strength: { min: null, max: null, drawn: 412, share: 412, kind: "procedural", basis: "plausible-procedural: corps figure shared by regiment count, Busey and Martin not available. Share 412 = ...", tier: "plausible-procedural", weak_source: true, sources: [...] }`. `drawn` is the number of figures the renderer instances (one soldier per figure, no cap) and is `0` for a unit that is not drawn; `share` is the procedural value whether or not the unit is drawn. A strength with `min === null` may never be `documented`. A printed figure is `kind: "printed"` with `min === max` (the PDF declares no range, so none is invented). The card prints `strengthText(u)` and the basis; `strengthDrawn(u)` gives the figures drawn.
2. **An arrival may have no entry.** `entry: null` with `entry_status` (a sentence saying why: no road of approach is printed, the road does not cross the loaded ground, a formation above the regiments, ...) is an open gap, not a guess. An arrival with an entry also carries `entry_status`. Arrivals exist for every unit that can be on the field (never-on-field units have none; the stage treats a missing arrival as "never present").
3. **Units carry how they are drawn.** `drawn` (boolean), `render: { status, reason }` where status is `moving` (a road of approach and a dated place), `edge_only` (a road of approach, no place after arrival: the unit waits in its column outside the loaded ground), `not_drawn` (open gap: no road of approach), `aggregate` (a formation above the regiments), `not_on_field` (PDF gating rule 2). The unit's `tier` is the tier of how it is drawn (`plausible-procedural` for drawn units, `open gap` for a leaf with no place, `inferred` for formations); strength, formation, arrival and entry carry their own tiers.
4. **Layer-level helpers.** `meta.linkedConflicts` is the list of conflict ids whose chosen value the layer uses (the shell fills `scenario.optionText` for exactly these); `layer.slotOf(unitId) -> { lng, lat, heading_deg } | null` is where the unit ends up (the renderer's slot), `layer.focus` is the index of a placed unit for the ground view, `layer.counts` the status counts, `layer.report(scenario).defects` the late arrivals (see the notes file).

`objects` entries may have `line: null` and `at: { place, lng, lat, sigma_m }` instead: no work or wall of the record has a mapped line in the repository, only a location text; the overlay draws a ring of the place's sigma and names the place.

What the shell builds from a real layer: `src/world-from-units.mjs` (one world unit per layer unit in layer order, `strength.drawn` soldiers each, a parked dummy gun record because the renderer needs one). The stub's `binding` is not needed.

Scenario handling in the real layer: a chosen value is applied only to the gates the ledger links to that conflict as an arrival (`topic_arrival`, `cited_by_reference`), and only through a clock the value prints, `noon`, `dawn` (the ephemeris table's civil dawn), or a labelled convention (`dusk`/`evening` 19:32, `night` 20:04, the checker's NAMED_PERIODS); a value that carries none leaves the gate as it is and says so in the arrival's `note`. `range` draws from the earliest printed value and says so. A gate that is only a date or an event floor is never drawn before its parent's time.

## Contract 1.2: what the second pass of the real layer added (shapes of 1.0 and 1.1 unchanged)

1. **Units carry how they come to be drawn.** A drawn unit has `approach: { id, road, phrase, row, cell, owner, owner_level, inherited, tier, column: { index, size, basis }, register, text }`: the nearest printed road of its own line of command (`inherited` is true when the road is printed for a formation above the unit), `tier` is `inferred` where the road is printed for a formation below the corps or for the unit itself and `plausible-procedural` where only the corps-level road is printed, `column.index` is the place in the column (roster order = the ledger's order; the order of march within a column is an open gap, register EG-0005). `notes` repeats it in words, and for a unit whose first place lies far from its entry it says: "Enters the map where X leaves the loaded ground; the ledger time (hh:mm at P) refers to a place D km farther on". An arrival's `tier` is the weaker of its gate's tier and its approach's tier, and its `entry_status` names the approach.
2. **`report(scenario)` has `offsets` as well as `defects`.** `offsets` (`kind: 'ledger_vs_edge'` or `'cascade'`, with `unit, stop, place, documented, arrives, late_min, distance_m, road`) is the ledger time of a unit's first place against the edge of the loaded ground: a data property, not a defect; the gate is not moved and the march is not shortened. `defects` is lateness of another cause (for example a chosen step-off clock). `activity_notes` lists the activities that were not applied and why.
3. **Events.** `leave` is emitted only for a departure clause (a printed time and a gazetteer road): the unit marches to the point where the road leaves the loaded ground, then `leave`. `activity` events other than the march/stand/halt of a path come only from an activity clause (`build_works`, `camp`, `rest`, `serve_guns`, `gallop`, `halt`, `stand`, `march`, `double_quick`), applied when the unit stands still and never before the clause's time.
4. **`data/placement.json` version 2.** `clauses` lists every clause of the four position cells of the 44 ledger rows (`status` transcribed or unresolved with `reason`; transcribed ones carry `kind`, `units`, `place` or `places` with the gazetteer's `sigma_m`, `t`/`t_to`/`depart` as printed or a labelled named-period convention (`t_basis: 'convention'`, `period`), `tier`, `sources` as printed); `approach`, `positions`, `activities` and `departures` are the entries that drive geometry and events, each naming its clause. Built by `tools/build-placement.mjs` from `tools/placement-clauses.mjs`.

## Contract 1.3: casualties, guns, per-figure kit and change of formation (shapes of 1.0 to 1.2 unchanged)

`src/history/contract.mjs` validates all of it (`validateCasualties`, `validateGuns`, the `state` and `formation` branches of `validateEvents`); `tests/casualties.test.mjs` and `tests/manifest.test.mjs` run the validators, and `tests/casualties.spec.mjs` runs it in the page.

1. **Units carry `casualties`.** `{ kind: 'printed' | 'procedural' | 'none', total: { printed, min, max }, fates: { killed|wounded|missing: { point, min, max } }, basis, fate_basis, tier, printed_tier, weak_source, sources, pool_owner, windows: [{ from, to, clauses }], engagement_clauses, engaged }`. `printed` is a figure printed in the PDF B.3 table (13 corps rows and 8 brigades, Stone Sentinels, a weak source); `procedural` is a share of one of them (never documented: the validator rejects `tier: 'documented'` and a `weak_source` other than `true`); `none` says why no number is assigned. `total.printed` is the figure that drives the picture, `total.min` equals it and `total.max` applies the army-level source spread; the three fates are ranges from the lowest and highest fraction any source gives (`data/casualty-sources.json`) and their `point`s add up to `total.printed` exactly. No regimental casualty number is in the record and none is read.
2. **`state` events** (`agent`, `fate`, `strength_now`, `killed`, `wounded`, `missing`, `down`, `tier`, `weak_source`, `sources`): one per man who falls while his unit is on the map and standing, in the printed engagement windows only (`windows`, from `data/engagements.json`), placed by the sim's loss solver with the counter-based RNG, so a seek equals sequential play. A loss whose time falls where the unit is marching in or away is not emitted; `report(scenario).casualties` lists, per unit, `plan_events`, `shown`, `not_shown` and the fates shown. The running ranges are the unit's final ranges scaled by the men fallen so far.
3. **The stage and the renderer.** For each `state` event of a killed or wounded man the stage writes the man's fall time into the soldier table (`sold1.x`, in the renderer's own animation clock; `stage.rebase()` after every seek) and, from then on, rewrites his slot in the unit's frame every time the unit moves or turns so that he stays where he fell. `RenderHost.uploadSoldiers(['s0','s1'])` writes the tables (WebGPU buffers, WebGL2 textures) only when `stage.dirtySlots` or `stage.dirtyFalls` is set. The prototype renderer and its shaders are imported unchanged.
4. **Units carry `guns`.** `{ status: 'drawn' | 'not_drawn' | 'not_applicable', count, types, printed, kit_battery, tier, weak_source, sources, reason, crew_per_gun, limbers }`. `drawn` needs a gun count STATED in `kit/artillery_batteries.json` for a battery that is drawn; no default count is ever applied; a kit entry that joins batteries is not split. A drawn battery gets that many pieces and a detachment of nine (gunner and Nos. 1-8: `CREW_POSTS` in `src/world-from-units.mjs`) out of the battery's own figures (the total stays the strength figure); limbers, caissons and teams have no model and are listed on the card. `data/battery-guns.json` (built by `tools/build-guns.mjs`) holds the match.
5. **Per-figure kit.** `layer.figures` (null without kit data), `layer.figureManifest(unitId, k, t, scenario)` (null before the unit enters), `layer.figureSummary(unitId, t, scenario)`, `layer.figureVari(unitId, k)` and `layer.rendererSupport`. A manifest is made by `src/history/manifest.mjs`, the port of `check_kit.manifest_for`, from the unit's kit record (`data/kit-crosswalk.json`, written by `tools/bt/kit_crosswalk.py`) or the default of its army and arm; a disputed unit returns `{ disputed: true, variants: { name: manifest } }` and chooses none. The B.6.12 validator is run in Python over every figure drawn (`tools/bt/check_figures.py`, result in `data/figures-validation.json`).
6. **Formation.** `unit.formation.changes: [{ id, to, t, phrase, stop }]` lists the printed changes of a drawn unit; a `formation` event is emitted at the clause time (or when the unit has arrived at the place the clause drives, or when its march ends). `FORMATIONS_DRAWN` = `line`, `column_fours`; any other value is valid in the contract and is listed in `stage.unsupported`, never dropped silently.
7. **Source keys added** for the new sections: `PDF-B1`, `OR27-CAS`, `PDF-TL`, `KIT-GUNS`, and the kit's own source keys for a gun count (`SS-ArtReserve`, ...).

## Contract 1.4: entries read from the Official Records position ledgers, and the provenance of a unit (shapes of 1.0 to 1.3 unchanged)

`data/placement-claims.json` (version 1, built by `tools/build-claim-placement.mjs` from the reviewed table `data/claim-curation.json` and the ledgers `history/positions/positions_{A,B,C,D}.jsonl`) carries `approach`, `positions`, `departures` and `activities` entries in the shapes of `data/placement.json` (the `Placement` class merges them after the entries of the PDF ledger rows: AP-08 onward, PO-62 onward, DP-01 onward) with these differences, and `src/history/placement.mjs: validateClaimEntry` refuses any entry that breaks them:

1. **Source.** An entry names `claim` (the primary ledger claim), `claims` (it and the claims that support it), `ledger` (A, B, C or D) in place of `row`/`cell`. `claims` of the file is `{ id: digest }`: the claim's id, ledger, unit, kind, tier, `fidelity`, the report id, author and printed page (`interpolated` where the page is a range), the verified quote (under 15 words), the printed `when` (printed words, date, `t_iso`, `approx`) and `place` (printed words, `gazetteer_ref`, `direction_or_road`), `conflicts_with`, `ocr_uncertain`; the digest equals the ledger line (tested).
2. **Use.** Only claims with `claim_support_verified` true and `fidelity_check` `passed_full_read` or `corrected` and a tier of `documented` or `inferred`; ledger B only after `RECHECK B COMPLETE` is the last line of `positions/RECHECK_B_NOTES.md`. The loader refuses a digest that does not satisfy this.
3. **Phrase.** `phrase` (at most 15 words) is literally in the claim's `quote`, its printed `place.printed` or its non-bracketed `direction_or_road` (`phrase_in`), or in the OR record named by `record` (`phrase_in: 'record'`; confirmed by `tools/verify_claim_phrases.py` into `data/claim-phrase-verification.json`, which the tests re-run when the OR text is present).
4. **Time.** `t_basis: 'printed'`: `t` equals the claim's `t_iso` and the claim's printed words give that clock; `t_basis: 'convention'`: a named period (`night`, `evening`, `dusk`) printed in the claim's own words (not in a compiler's parenthesis) takes the labelled convention of `placement.mjs` (`PERIODS`) on the claim's date; a printed clock always outranks a convention.
5. **Place and road.** A position's `place` is the gazetteer place the ledger references for the claim, named in its printed words, inside the loaded ground, with the gazetteer's `sigma_m`; a road is a gazetteer line (an approach road must cross the loaded ground). The file holds no coordinate.
6. **Tier.** `tier` is `inferred` (the place or road is a gazetteer entry, which is inferred; a claim never makes a placement `documented`); `claim_tier` is the tier of the claim (`documented` or `inferred`, the card says so); `identification` says how a printed name that is not the gazetteer's name was read, where it was not read from a name.
7. **Conflicts** (`conflicts`): `{ kind, unit, claims, values }`, at least two claims or entries and both values: `approach_roads_differ` and `stop_hour_differs` (neither side is placed), `claim_differs_from_ledger_row` (the PDF entry stays as it is; the claim is not applied), `approach_refines_formation_above` (the unit's own printed road is the nearer and is used; the road of the formation above is listed). `corroborations` lists claims that agree with an entry in use; `units` gives, per unit, how many claims name it and why they are not used.
8. **History layer v4 (no change of the contract; the shapes of 1.0 to 1.5 are as above).** An `approach` entry may carry `added_in: 'v4'` (the roads added by the audit of `APPROACH-AUDIT.md`, AP-31 and AP-32; the audit builds the v3 layer by leaving them out); a curation row of `phrase_in: 'record'` may carry `window_chars` (600 to 2000, default 600) when the sentence that prints the road stands further than 600 characters from the claim's quote, and `data/claim-phrase-verification.json` then records the window. An approach needs a road and no clock: its time is the unit's gate (Q04), whatever the claim prints, so a claim without a clock may name a road of approach (the first review already read them; the claims without a clock that were dropped are candidates for a stop). `unit.approach.text` of a unit whose road is read from a claim now ends its first part with “Documented: the road of approach ... Modelled: when the unit reaches the edge of the ground ... and its place in the column”; no field was added to `unit.approach`.

9. **History layer v5 (DEC-013 a, DEC-014; no change of the shapes of 1.0 to 1.5).** An `approach` entry may carry `added_in: 'v5'` (AP-33 to AP-41; the audit builds the v4 layer by leaving them out) and, besides the fields above: `claim_kind` and `admitted_by: 'DEC-013a'` when its claim is of kind `position` or `night_position` (admitted only if its printed words put the formation ON the road before it reached the field; the builder refuses any other use of such a kind and requires `identification`); `concordance: { id, period_name, printed_name, tier, summary, file }` when the road is printed under a period name that the gazetteer does not hold (the id is a RESOLVED entry of `data/road-concordance.json` that covers the claim, names the same gazetteer road and lists the printed name among its variants; the names stay unresolved in `Gazetteer.resolve`); and `inference` (one sentence saying so; the card prints it as “Inference: ...”). `data/road-concordance.json` (built by `tools/bt/roadconc/build_concordance.py`, read by the builder and the tests, not by the page) holds `names` (status resolved / resolved_name_no_approach / unresolved, tier inferred or documented, variants, evidence with OR quotations verified in the text and period-map crops, argument, rejected alternatives, claims, the crossing of the resolved road with the edge of the loaded ground), `forms`, `crossing_checks`, `georeference` (transform and error of each map read), `sources_read` (SHA-256) and `traced_roads` (empty: no line was traced). `placement-claims.json` may carry `approach_block: [{ unit, claims, values, reason }]`: a unit that takes no road from a formation above because reports of the unit print another road and disagree (`Placement.blockOf`, `approachInfo` returns null); its plan has `status: 'unresolved'`, `blocked: true` and a reason naming both roads and the claims, and the claims are digested so that the card lists them. `unit.approach.text` of a v5 unit ends as in v4 (“Documented ... Modelled: when the unit reaches the edge of the ground ... and its place in the column”), with the sentence of the `inference` first.

`data/claim-dispositions.json` gives one row for every claim read (used, used as support, recorded and inert, recorded and not applied, or left out with a reason code and the reason in words) and the claims earlier than their unit's ledger gate; it is read by the notes and the tests, not by the page.

**`unit.provenance`** (null when no claim names the unit or a formation above it): `{ entries: [{ kind: 'approach' | 'stop' | 'departure', entry, via (the formation the entry is set for, null for the unit itself), claim, claims, phrase, phrase_in, road | place, t, t_basis, period?, approx?, tier, claim_tier, identification, applied, why_not }], claims: { id: brief digest }, peers: [{ of, peer }], conflicts, summary: { read, used, codes } }`. `applied` says whether the entry drives this unit; if not, `why_not` says why (no road of approach so the unit is not drawn; before the unit's own ledger gate, Q04; a nearer entry within 90 minutes replaces it; the unit already stands at the place). `peers` are the claims the ledger lists as conflicting with a claim used (only usable ones), each with its report, page, quote and printed time and place; none is chosen. `validateProvenance` (contract.mjs) refuses a claim with a fidelity check other than `passed_full_read` or `corrected`, a quote over 15 words, an entry without a claim or a phrase, an entry tier of `documented`, an unapplied entry with no reason, and a conflict that lists fewer than two claims or values. A unit that has a claim-driven approach also has `approach.claim`, `approach.claims`, `approach.ledger`, `approach.report`, `approach.page`, `approach.claim_tier` and `approach.phrase_in`; `unit.sources` gains the key `OR27-POS`.

Columns of different approaches on the same road queue one behind the other, earliest gate first (`planTracks`), so that a column that waits at the edge is not stood on by a later one.

## Contract 1.5: day-level positions of the troop maps (shapes of 1.0 to 1.4 unchanged; DEC-010, DEC-011)

`data/daypositions.json` (version 1, built by `tools/build-daypositions.mjs`) is a digest of the 484 claims of `history/positions/troopmap_jul{1,2,3}_b1876.jsonl` (Bachelder 1876 sheets 1 to 3, sheet keys `J1`, `J2`, `J3`) and `troopmap_jul1_hour_loc99447494.jsonl` (LOC 99447494, sheet key `H`): per claim the id, sheet, unit, kind (`position` or `movement`), tier, fidelity check, `verified`, the printed label, the quote, the printed clock fields as the claim carries them (`t_iso`, `t_start_iso`, `t_end_iso`, `clock_attachment`), `lng`, `lat`, `sigma_m` (the claim's own, never changed here), the reading basis, scan pixels, the crop and its spec, the report id and `nw_of_seminary` (sheets 2 and 3: the claim lies north-west of the Seminary Ridge proxy, where the registration is untested, ACCURACY.md); `sheets` gives each file's sha256 and claim count. `tests/daypos.test.mjs` re-reads the four files and compares every field of every digest; `src/history/daypos.mjs` (`DayPositions`) refuses a digest that is not verified, not read by eye, of a tier other than documented or inferred, an hour-sheet claim that is documented, an unknown unit or a wrong date. The layer built without the file (`raw.dayPositions` null) produces exactly the contract 1.4 events and arrivals (tested).

1. **What a position is.** Day level: where the unit's line stood on that day, never at a minute (the sheet merges first, intermediate, evening and all-day line states; no state is read for any single-label symbol). Tier `documented` for (unit, place, day) only; the claim's own tier (`documented` or `inferred`) is carried and printed. A compiled map of 1876, not independent of the Official Records. Source keys `BACH-1876-S1..S3` (secondary, not weak) and `LOC-99447494` (secondary, weak: author and date unknown) are added to `sources`; the event tier is `plausible-procedural` because the time is modelled.
2. **Which positions are used.** Rule 1: a unit's position on a sheet only if it has exactly one claim on that sheet (a second label, even a movement arrow, makes it several line states: none is drawn, all are listed). Rule 2: levels brigade, battery, artillery brigade, artillery battalion and artillery group place their regiments or batteries inside the position (the placement slot rule, with the claim's sigma); division, corps and army labels place nothing; the nearest unit up the line of command that has any label on the sheet is the only one consulted. Rule 3: the hour sheet only as an inferred timed stop (arrival just in time for 14:00 and no later than 15:30 on 1 Jul) where the unit has no single-label position on sheet 1 and no timed ledger place dated 1 Jul. A position outside the loaded ground, or whose laid-out column would stand partly outside, is not drawn (the reason is on the entry). A day position never gives a unit a road of approach: a unit with no road stays an open gap and its card lists the position.
3. **Times.** Modelled per scenario by `real.mjs`. A day stop leaves as soon as it may (not before the unit's start at its gate, not before local midnight of its day, not before an engagement window still running at that midnight ends), marches at the march rate (1.25 m/s) from the edge along the approach road or straight from the previous position, and arrives no earlier than that and no later than the end of the day, the clock printed in the label's own run (`same_run`) if there is one, or the departure the next timed place needs. It is put in the first gap of its day in which every timed ledger place is reached no later, and at no faster a gait, than without it; if none fits it is not applied in that scenario (`report.day_stops[].why_not`). A ledger place of the same date that overlaps the position within the two stated sigmas takes its slot inside it (the ledger keeps the time; `plan.stops[].refined_by`).
4. **`unit.day_positions`** (null where no sheet names the unit or a unit above it): `{ days: [{ sheet, date, source, sheet_label, status ('single'|'multiple'|'movement_only'|'formation'), why, owner, owner_level, via, labels, claims: [ids], used (claim id or null), drawn_as ('placed'|'not_applied'|'not_drawn'|'not_used'|'aggregate'|null), why_not, role, entry, refined_stops, ledger_compare: [{ entry, source, place, t, tier, distance_m, sigma_place_m, sigma_day_m, agree }] }], hour: <same shape or null>, rules }`. Only `single` has `used`; only a unit that is drawn is `placed`; `ledger_compare` lists, for the claim's date, every timed place of the PDF ledger rows and of the OR27 position-ledger claims for the unit or a formation above it with the distance between the two (both are shown, neither is chosen). `validateDayPositions` (contract.mjs) refuses a position drawn from several labels, a placed position on an undrawn unit, a missing reason and a malformed comparison. `layer.dayClaims` is the digest, `layer.dayPositions` the loader.
5. **`report(scenario)`** gains `day_stops` (one per drawn leaf unit and day entry: `applied`, `merged_into` (a ledger stop inside the position reaches it), `why_not`, `arrive`, `depart`, `distance_m`, `latest_arrival`, `window`, `required_by`, `hold_until`), `ledger_arrivals` (the arrival minute of every timed place) and `final_slots`. `layer.plans.get(id).days` is the scenario-independent geometry of the day entries (`slot`, `window`, `feasible`, `compare`, `refined_stops`) and `plan.stops` remains the ledger stops only.

## Contract 1.7: line states of the troop-map labels as windows of the day (shapes of 1.0 to 1.6 unchanged; DEC-017, DEC-018)

`data/daypositions.json` is **version 2**. Besides the 1.5 fields each claim carries the line state read by eye (`library/LINE-STATES-NOTES.md`): `line_state` (`first` | `intermediate` | `evening` | `all_day` | `mixed` | `unreadable`; null on the hour sheet), `line_states` (the two states of a mixed label, else null), `line_state_basis`, `line_state_crop`, `line_state_read`, `line_state_prev`, `printed_clock_near_line` (verbatim) and the computed `line_clock: { text, hhmm, iso, complete, usable, why } | null`, where `complete` means the whole printed text is an hour, optional minutes, A.M. or P.M., and `usable` means complete, not classed `adjacent_unproven` or on an arrow by the earlier pass, and agreeing with any `t_iso` that pass read (`daypos.mjs` `parseLineClock`, `lineClockOf`; the tests recompute both for every claim). `DayPositions.validate` refuses version 1, a state outside the vocabulary, a mixed label without two or more states, `line_states` on a label that is not mixed, a state without its basis and crop, a line state on the hour sheet, a printed clock without its reading and a `line_clock` that does not follow from the printed text.

1. **Labels (rule 1 of 1.5 extended).** `onSheetFor` returns status `single` (one position claim; `items` has one entry, its state null where none was read), **`sequence`** (several position claims whose states order them: `orderStates`; `items` lists one entry per claim and state in the order first, intermediate(s), evening; a mixed label contributes both its states; `used` is null; `order_why` says what orders them) or `multiple` (several labels the states do not order: two or more bars of one style, an all-day bar beside another state, a label with no readable state, two or more intermediates without a distinct usable clock on each, clocks that contradict the order, or a movement arrow among them; `order_why` says which; nothing is drawn, as in 1.5). `itemsOf(res)` collapses consecutive items of one claim (a mixed label alone is one item `mixed`) and gives each item its entry id `DAY-<claim>`, or `DAY-<claim>#<state>` when one claim gives two items with another between them, and the ids of the items before and after it. The hour sheet is used only where sheet 1 gives neither a single nor a sequence.
2. **Windows (rule 3 of 1.5 extended; `STATE_RULE` carries the wording).** Each `plan.days[]` entry is one claim and state and carries `state`, `states`, `state_basis`, `state_crop`, `state_read`, `clock_text`, `line_clock`, `state_clock` (minutes of a usable clock, else null), `arr_rule` (`asap` | `clock` | `midpoint` | `evening`), `arr_target`, `arr_by` (soft: the usable clock, else the same-run `required_by`, else the evening convention for first, intermediate and evening lines; null otherwise), `evening` (the convention in minutes for the sheet's date: `eveningOf`, the start of [DUSK] 19:32 LMT of `arrivals.mjs` NAMED_PERIODS, `EVENING_BASIS`), `seq: { status, index, of, prev, next, why }`, `state_tier` (`documented` for a read state, else null) and `state_time_tier` (`documented` with a usable clock, else `modelled`; null without a state). `real.mjs` schedules a day stop at the march rate, leaving as soon as it may (`asap`), or so as to arrive at the usable clock (`clock`), at the middle of the window between the earliest the march allows and `arr_by` (`midpoint`), or at the evening convention (`evening`) when the unit has a known place of the same day to stand at before (the item before it in the schedule stands on that day), else as soon as it may; a state item is inserted after the item before it in its sequence; arrival after `arr_by` is a **state offset**, never a moved gate or a dropped timed place.
3. **`unit.day_positions.days[]`** gains `status: 'sequence'`, `order_why`, `evening` and `items: [{ entry, claim, state, states, index, of, prev, next, state_basis, state_crop, state_read, clock_text, line_clock, state_clock_used, rule, state_tier, state_time_tier, arr_rule, drawn_as, why_not, refined_stops, ledger_compare }]` (one item for `single`, two or more for `sequence`, none otherwise); the entry's `drawn_as` is `placed` if any item is placed, `why_not` lists the items that are not; `unit.day_positions` gains `evening_basis` and `decision: 'DEC-018'`. `validateDayPositions` requires a `single` to have one item and a `sequence` two or more with `order_why` and `used` null, a `multiple` to say `order_why`, and each item to name its claim, carry a state from the vocabulary (or null), and with a state its basis, crop, `state_tier` documented, `state_time_tier` documented only with a usable `line_clock`, and the rule of its window.

## The structures layer (not part of the history-layer contract; unchanged contract 1.7)

The history-layer contract above is unchanged.
