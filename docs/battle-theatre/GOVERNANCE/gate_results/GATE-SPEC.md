# GATE-SPEC: the 28 gates, reconciled

Written 2026-11-13 (UTC) by workstream bt-gates and corrected the same day after an independent review (what was found and changed is in 11.4). This file reconciles `GATE-SPEC-A.md` (the gates defined from the governing text) and `GATE-SPEC-B.md` (the gates seen from the implementation, with its evidence folder `spec-b-evidence/`). **Where the two differ, or where either differs from the code, the test files, the realization harness or the plan's own gate text, this file governs and the stricter reading wins; every such difference is listed in section 8.** The two inputs are left unedited in this folder as the record of what each said. Governing text: `BIBLE/plan-clean.txt`, the 144-page "Gettysburg Total War animation plan, version 2" (marker `=== PAGE n ===` equals the printed "page n of 144"). Project rules: `CLAUDE.md`. Decisions: `GOVERNANCE/decision_log.md` and `GOVERNANCE/decisions/DELEGATED-DECISIONS-2026-11-11.md` (entries DD-nn, DD-G01 to DD-G12 for gate settings and readings, DD-RZ-01 to DD-RZ-04 for the realization harness).

What this file is: the definition a runner must implement and a reviewer must apply. It sets no `passes` flag, runs no gate, edits no data and lowers nothing. A number quoted here was read from a named page or file. Where the plan gives no number the file says so and marks anything it adopts as ADOPTED-PROVISIONAL under a recorded decision; it is never presented as the plan's. Statements about what exists today are true of the working tree at the time named and are marked as read from `GATE-SPEC-B.md` when this file did not re-run them.

**Citation form.** `(p. 136, Q)` is page 136, Part E, Section Q. `(p. 62, B.2.5)` is page 62, Part B. `(App. B, pp. 138-139)` is an appendix. A quotation inside double quotes was matched by script against the plan page it is cited to (section 11 states what was run).

**Ambiguity rule.** Where the text can be read two ways, this file takes the reading under which fewer items can reach PASS. The looser reading is never used silently; each choice is an A-nn entry (ambiguity of the plan's text, ids unchanged from `GATE-SPEC-A.md`, section 9) or an X-nn entry (disagreement between the two specs, the code or the harness, section 8).

## 0. Key rulings in one place

1. **K1 Pass is a conjunction.** `passes=true` needs every applicable gate to give PASS for the sub-requirement's items, the class rule (section 4), an admissible `source_status` (section 5) and U-02 P2 to P6. A gate PASS is necessary and never sufficient.
2. **K2 Linked is not passing.** A link to a register entry is never a pass. A non-passing sub-requirement is LINKED-ACTIVE only at link level L3 (complete entry, marking in the product, dated machine-readable search of the acquired library, reconstruction present in the product build); Q18 counts PASSING or LINKED-ACTIVE (1.4, X-02, X-03).
3. **K3 COVERED has a narrow reach.** COVERED (the gate's own register or flag branch) exists and counts toward a gate verdict only where the gate text has that branch: Q07, Q08, Q17, Q19, Q25, Q28. For Q05, Q09 and Q14 a COVERED item is reported and keeps the verdict INCOMPLETE. COVERED never gives `passes` (X-09).
4. **K4 A card is not a visual realization.** A row with no scene consequence, and every open-gap row, is covered only by an L3 entry (and, for an open-gap row, the visible gap marker). Q17 rests on the strict reading (section 6, X-05).
5. **K5 Documented means matched.** `documented` needs a non-lead source and a short extract (under 15 words, p. 134, E.6) that the runner re-matches in the stored source text in the run; a stored flag is not evidence. Leads (Wikipedia, forums, blogs, auction pages, wikis) never support a documented datum (p. 134, E.1, E.2, E.7).
6. **K6 State rows are judged by every object they name.** An object no gate covers (a road, a cemetery ground) blocks the row; an empty domain is never a pass (3.2, A-12).
7. **K7 Top-level rows aggregate.** A row `R01.0000` to `R22.0000` is covered when every child (the other rows of the requirement, the populations of 4.11 and the requirement-level check items RC-Rnn.k of 7.1, so that no requirement is childless) is PASSING or LINKED-ACTIVE, and passes only when its Appendix E gates, its requirement-level checks and every child pass; R03.0000 never passes (4.9).
8. **K8 Thresholds are recorded or unset.** A threshold is a recorded value (DD-G01 to DD-G06, DD-G09 and DD-G10, DD-RZ-01 to DD-RZ-04 as limited by DD-G09, the plan's own figures) or UNSET, and an unset one makes the gate INCOMPLETE. No runner loosens one (1.7).
9. **K9 Owed is owed.** Anything that needs the real GPU, a listener, the owner's caps or a purchase is NOT-RUN or INCOMPLETE, written as owed with the exact step, never claimed.
10. **K10 Every means every.** A check that says "every" runs over the whole domain: the scenario set S* and the time grid of 1.5. Work may be chunked and resumed; a sample never gives PASS (U-26).
11. **K11 A gate must be able to fail.** Every check has a negative control (an injected defect it must catch); a runner without one is not accepted (U-25).
12. **K12 One result file per gate.** `GOVERNANCE/gate_results/Qnn.json`, per item `id`, `pass`, `reason`, `evidence`; `pass` is true only for result PASS (1.6, X-01).
13. **K13 No circular support.** Statuses are computed in strata: every gate except Q18 and the requirement-level checks first, then the status of every leaf row, then the derived coverage of the 22 top rows, then Q18, then `passes` of the leaf rows and last `passes` of the top rows. Q18 reads statuses and never a `passes` flag, and a top row's `passes` is an input to no gate and to no child, so R01.0000, which lists Q18 among its gates, is not its own support (4.9 TOP-5, X-42).

## 1. Common machinery

### 1.1 Terms, item results, verdicts

| Term | Definition |
|---|---|
| Item | The smallest thing one gate judges: a unit in a scenario, a timeline row, one state change of one object, a datum class scanned exhaustively, a night frame region. Each gate in section 2 names its item. A class of data judged by an exhaustive scan may be one item whose evidence lists every failing member; an item is never coarser than the gate text allows (K10). |
| Sub-requirement (S-R) | A row of `requirements.json` `sub_requirements` (966 rows today: 957 `origin: pdf`, 9 `origin: owner_chat`). Its text is never edited: "you may never delete or reword one" (p. 134, F). |
| Subjects | The entity ids an item is about (unit ids, structure ids, work ids, row ids, content classes). The apply script joins items to S-Rs by `sub_requirements` (the item's own S-R) and by `subjects` (the entities a timeline row's realization record names, section 6). |
| Link level | L0 to L3: how far an S-R is tied to an open Evidence-Gap Register entry (1.4). |
| S-R status | PASSING, LINKED-ACTIVE, LINKED, UNLINKED (1.4). |
| Scenario set S* | Every selectable combination of source-conflict values that can reach an item (1.5). |
| Renderer class | `python`, `node`, `swgl` (software GL in a browser here) or `gpu` (the owner's GPU, NOT RUNNABLE HERE) (1.8). |

**Item results** (the value of `result`; `pass` is true only for PASS):

| Result | Meaning |
|---|---|
| PASS | The property holds for this item and the run record names the evidence. |
| COVERED | The item does not meet the PASS branch but the gate's own register or flag branch is fully met (an L3 entry, the visible flag, the stated window). Counts toward a verdict only for Q07, Q08, Q17, Q19, Q25, Q28 (K3). Never toward `passes`. |
| FAIL | The property is violated (an entity before its arrival window, a modern object in the scene, an unmarked procedural item, a missing datum, an object not drawn). |
| NOT-RUN | The check could not be executed here (real GPU, missing tool, blocked host, a spec that printed `# NOT RUN (NEEDS_GPU)`, a skipped test). The record states why. Non-passing. |
| BLOCKED-INPUT | An input the gate names does not exist or is not eligible (no verified OOB table, no documented camera position, no cap set, a source text not on the machine). Non-passing. No vacuous pass (U-03). |
| N/A | The gate's domain excludes the item. N/A never satisfies an item whose every listed gate is N/A (U-03). |

**Gate verdict.** PASS: at least one in-domain item exists, every in-domain item is PASS (or COVERED where K3 allows it), and none is FAIL, NOT-RUN or BLOCKED-INPUT. FAIL: at least one FAIL. INCOMPLETE: no FAIL, but at least one NOT-RUN, BLOCKED-INPUT, a COVERED item of a gate outside K3, an unset threshold, an incomplete scan, or an empty domain. Exit code of the runner: 0 PASS, 1 FAIL, 2 INCOMPLETE, 3 runner error.

### 1.2 Universal rules

Each rule cites the text it comes from. U-01 to U-24 keep the ids of `GATE-SPEC-A.md`; U-25 to U-28 are added by this file.

- **U-01 Gate pass is necessary, not sufficient.** "A sub-requirement passes only when its gate passes" (p. 136, Q). `passes=true` needs (a) every applicable gate in `gate_ids` plus the domain gates of 3.2 and 4.x to give PASS for this S-R's items (A-02: `gate_ids` with several gates is a conjunction), (b) the class rule of section 4, (c) an admissible `source_status` (section 5), (d) P2 to P6 of U-02.
- **U-02 What PASS means for an S-R.** P1 the item results are PASS (U-01 a). P2 evidence sufficiency: the tier the product shows does not exceed the evidence status (1.3, section 5). P3 marking: every non-documented content of the item is marked (the Q23 item is PASS). P4 conflicts: every source conflict that reaches the item is carried as a selectable scenario and the item passes in each (A-06). P5 no content gap: an item whose own content is an open gap, a failed lookup, an unsupported claim or lead-only support never passes. P6 provenance of the run: command, versions, input hashes, renderer class and date are recorded (1.6) and any renderer-dependent part is listed as owed on the GPU.
- **U-03 No vacuous pass.** An empty domain gives BLOCKED-INPUT, never PASS. An S-R whose every listed gate is N/A for it cannot pass by that; it needs the domain gate of 3.2 or section 4 to pass, otherwise it stays LINKED.
- **U-04 Linked is not passing.** Section Z item 1 reads "every in-scope sub-requirement passes or is linked to an open register entry with an active reconstruction" (p. 138, Z); F (p. 134) and Q18 (p. 136) say the same: passing and linked are two different states. A link never turns a FAIL, NOT-RUN or COVERED item into PASS (A-03).
- **U-05 No lowering, no skipping.** "Never lower a threshold to pass" (p. 136, Q). A gate, threshold, scenario, row or class is never narrowed, disabled or skipped to make an item pass (p. 138, Z; Law cl. 1 and 8).
- **U-06 Scope of time.** The whole window: 1863-06-26 00:00 through 1863-07-14 23:59 local mean time (LMT = UTC minus 5 h 09 min, p. 9, B.2 and p. 111, B.10.2) plus the epilogue days 1863-11-18 and 1863-11-19. The window starts June 26 or the owner's chosen start and ends at the owner's chosen end, "the notes cover the retreat through about July 14" (p. 137, T.4); the epilogue is R22 (p. 133, A; pp. 116-117, B.12). Narrowing is an owner decision (p. 130, D.8.2); DD-20 keeps the full window. All three battle days and all nights are in scope (p. 138, Y.12).
- **U-07 Scope of scenarios.** Every check that depends on a source conflict runs over S* (1.5). "Scan every frame range of every scenario" (p. 136, Q04).
- **U-08 Evidence.** A datum is `documented` only with a non-lead source that states exactly it and a short extract (p. 134, E.2 and E.6; p. 136, P.3; App. B, pp. 138-139). Wikipedia, forums, blogs, auction listings and wikis are leads (p. 134, E.1, E.2, E.7). A quotation is under 15 words (p. 134, E.6); the repository's working limit is 14 words.
- **U-09 Never fabricate.** No invented quotation, measurement, name, time, number, citation or URL; a failed lookup is recorded as failed (Law cl. 4, p. 132). A gate result never contains an extract the runner did not match in the stored source text.
- **U-10 Renderer class.** A node or python result cannot certify a property defined on the picture. A software-GL result is valid for properties that do not depend on the GPU (pixel statistics of a deterministic shader, draw-list contents, pixel identity between two runs) and is recorded `PASS@swgl` with "real-GPU confirmation owed". Frame time, GPU memory and the real-GPU baseline need `gpu`; the runner records NOT-RUN with the reason (this container has software rendering only). A visual result is claimed only for frames that were looked at (each picture item carries `looked_at: false` until a person or an engineer viewed the saved image).
- **U-11 Independent verification.** A fresh-context verification run per milestone, told to flag only correctness and requirement gaps; "Do not self-certify what you have not run" (p. 136, Q, last paragraph; p. 137, X.5). Its record is part of the milestone (Q27.5).
- **U-12 Records decide.** `passes` is a pure function of the latest valid run records (1.6). A record expires when an input hash it names changes. A failing, expired or missing record sets `passes=false`.
- **U-13 Literal compliance impossible.** The item is not exempt (Law cl. 3 and 5): the strongest evidence-based reconstruction is built, registered (tier, marking, owner question), marked in the product and escalated; the S-R is then at most LINKED-ACTIVE.
- **U-14 Visible gaps.** A missing-evidence item is shown as a marked gap (Law cl. 7; p. 9, B.2: "Nodes with tier open gap generate no behaviour and surface as map markers in the evidence layer"). A concealed gap is a violation: FAIL for Q23.
- **U-15 Reading the product.** Gates test what the page loads and draws (the shipped data, draw lists, the audio graph), not only source data. The history layer is read-only to renderers (p. 134, D). A result obtained on the placeholder layer (`?history=stub`) says nothing about the history and never counts as evidence for an item (X-31).
- **U-16 Owner-only acts.** A gate that needs an account, licence acceptance, payment, third-party contact, deployment or a cap value (p. 130, D.8) is INCOMPLETE with the exact owner step written next to it. Claude never performs the act (Law cl. 2; CLAUDE.md standing constraints).
- **U-17 Delegated defaults.** The owner delegated the default view of conflicts on 2026-11-11. A default chosen under that delegation is the default for Q02, Q19 and class CF only while (a) it is recorded as an entry of section A of the delegated decisions and as `conflicts.C-nnn.default_scenario_id` in `decisions/conflict_defaults.json`, (b) the product labels it "Default chosen under delegated authority, reversible by the owner" with its tier, (c) the plan's default and every other value stay selectable. The word DECIDED is never written to `decision_log.md` for it.
- **U-18 Clocks.** All times are LMT as printed. The roughly 20-minute Union and Confederate clock difference "is not applied to any row, it is carried as uncertainty" (p. 9, B.2). Nothing in a gate applies it: Q04, Q05 and Q06 are exact, and so is the match of a realization record to the time its row allows, which has no margin at either end (6.4 V4). The wider window that the realization harness uses as its own necessary condition (DD-RZ-02, a 20-minute margin at each end of a printed clock time) is not adopted by the gate (X-36, DD-G09).
- **U-19 Row identity.** Day-header rows of the timeline are not events (p. 9, B.2) and are not sub-requirements. Row ids T1-001.., T2-001.., T3-001.. (T3-131 absent) and E-001..E-014 are stable.
- **U-20 Thresholds.** Only recorded thresholds are used (1.7); an unrecorded one makes the gate INCOMPLETE.
- **U-21 Fresh state.** A run starts from the committed inputs plus the working-tree data it names by hash. It never reads a result file as if it were an input and never runs a script's `main()` that writes outside `GOVERNANCE/gate_results/` (X-30): it imports the functions or runs the command without its writing flag.
- **U-22 Heavy runs** (over about 30 s of CPU, every browser run) go through `tools/horde/bench.sh`, at most two at once, a timing measurement alone (`--timing`). A run waiting for the lock is not a failure. The job is started in the background, writes to a file and is waited for; it is not killed.
- **U-23 Copy audit.** Gate outputs under `GOVERNANCE` are not shipped. A gate assertion that reads shipped files (Q02, Q23) never writes or quotes how the site was produced into shipped files (CLAUDE.md; FINAL-ACCEPTANCE copy audit).
- **U-24 Product marking after DEC-006.** The "reviewed by automated subagents" label is dropped (DEC-006). Tier marking of non-documented content stays (Q23), as does the register.
- **U-25 A gate can fail.** Every check Qnn.k has at least one negative control in `tests/governance/gates/`: an injected defect (a unit placed before its arrival, a fence that does not change state, an unmarked procedural item, a quote that is not in the source) that the runner must report as FAIL. The test runs in the same suite as the runner.
- **U-26 Exhaustive or incomplete.** "Every", "at every" and "scan every" mean the whole domain and the whole grid (K10). A run that completes a fraction records the fraction and the verdict is INCOMPLETE. Results are cached by content hash (inputs, scenario, time, view) so that a resumed run skips finished chunks.
- **U-27 Skipped is not passed.** A test or spec that is skipped, or prints `# NOT RUN (NEEDS_GPU)` (`t.gpuOnly`, `t.notRun` of `app/tests/lib.mjs`), counts as NOT-RUN for the part it names (X-32).
- **U-28 Existing greens are inputs.** `check_structures.py` "ALL PASS", the node suite and the other self-checks validate data and engine consistency. They are evidence for an item and never a gate result (SPEC-B 5.4).

### 1.3 Evidence statuses and tiers

The vocabulary of `source_status` and its rule are section 5. Tiers (App. B, pp. 138-139): `documented` (at least one non-lead source with a short extract, the claim matches the source); `inferred` (`reasoning` required, premises documented); `plausible-procedural` (a complete `procedural` block: generator and version, seed, distribution, documented context, substitute; and a register entry when the gap affects a requirement). Items affecting a visible result need two independent sources (distinct `independent_of` roots) or a flag. `render_flag`: 0 documented, 1 inferred, 2 plausible-procedural. "Open gaps are not a tier: they are register entries" (p. 133, B); the timeline uses the category `open gap` for rows (p. 9, B.2) and it is shown as a marked gap, not as content. Substitute content (modern motion bases, synthesized audio, open textures) never receives the documented tier and is recorded in the asset manifest (p. 121, C.10).

**Effective tier** of a timeline row or datum, in order of precedence: (1) an accepted correction record (`timeline_corrections/`, `evidence_corrections/`) with a citation and passage; (2) `timeline_verified.jsonl` `tier` as adopted by DD-08 and DD-09; (3) the seed tier (`timeline_seed.jsonl`, never rewritten). The effective tier can only be lower than or equal to what the evidence status allows; a demotion is always allowed, a promotion needs a matched citation.

### 1.4 Register links: "open", "active reconstruction", link levels

"Open register entry" uses the statuses of Appendix A (p. 138): `open`, `awaiting owner`, `decided`, `closed`. A link counts only for `open` and `awaiting owner` (A-04, X-02). A `decided` entry means the owner or the delegate chose: the decision is implemented and the S-R must then pass on its own. `closed` entries do not count (EG-0007 and EG-0025 today). "Entries are never deleted" (p. 137, R).

| Level | Condition (all runner-checkable) |
|---|---|
| L0 UNLINKED | No `register_ids` entry with status `open` or `awaiting owner`. "Unfinished work, not an exception" (p. 134, F). |
| L1 LINKED-RECORD | At least one open entry whose fields are all present and non-placeholder: `title, rids, cat, desc, why, searched, subst, recon, tier, marking, status` and the owner-decision field `owner_q` (Z.3, p. 138: "a reconstruction, a marking and an owner-decision field"; App. A, p. 138: "Owner decision requested"). A placeholder is empty, `-`, `none`, `n/a` or the marker "not stated by the shard proposal". |
| L2 LINKED-MARKED | L1, and the marking is in the product for this item (the Q23 item is PASS; for a gap the visible gap marker with its register link). |
| L3 LINKED-ACTIVE | L2, and (b) the entry carries a dated machine-readable search log: a sidecar `GOVERNANCE/register/search_logs/<EG id>.json`, a list of `{source_id, locator, date_searched, result, note}` with `result` one of found, negative or unreachable naming the acquired sources that could settle the gap, each searched on or after the date that source was acquired (Law cl. 3a: exhaust the free primary-source library before settling for less); and (c) the reconstruction named in `recon` is present in the product build for this item: a datum, draw object, scenario or realization record that lists the register id and is loaded by the page, or, where the reconstruction is a marked gap with no generated behaviour, the marker object exists. |

**S-R status.** PASSING: `passes=true`. LINKED-ACTIVE: not passing, L3. LINKED: not passing, L1 or L2. UNLINKED: L0. The coverage condition of Q18 is PASSING or LINKED-ACTIVE for a leaf row (every row except the 22 top rows below) and COVERED-BY-CHILDREN for a top row (K2, A-05, K13). The existing `check_governance.py` and `check_coverage.py` count any entry whose status is not `closed` as a link (and `check_governance.py` omits `owner_q` from its field list): that is the weaker reading, reported as such, never as Q18 coverage. Today the register has 487 entries (485 open, 2 closed); counted with the placeholder rule above, 129 have no usable `owner_q` (108 empty), so L1 fails for them; no entry has a search log (the format above is new), so L3 is empty today.

**Top-level rows (`R01.0000` to `R22.0000`).** Their text is an aggregation ("all child sub-requirements pass or link ..."), so their coverage is derived and is never read from their own register link or their own `passes`: COVERED-BY-CHILDREN when the set of children is not empty, every child is PASSING or LINKED-ACTIVE and every expected population of 4.11 exists. The children of `Rnn.0000` are (a) every other row of requirement Rnn in `requirements.json`, (b) the populations of 4.11 once generated and (c) the requirement-level check items RC-Rnn.k of 7.1, one per test the plan prints for the requirement (71 items; they are what covers the 12 requirements that have a single row and no population, 4.9 TOP-1). The nine rows `OA01.0000` to `OA09.0000` are leaf rows (3.1, 4.10), not top rows. The `passes` of a top row follows 4.9.

### 1.5 Scenario space, time grid, entity classes

- **Scenario.** A function from every conflict to one of its values: C-001..C-047 and the further conflicts the plan prints elsewhere (A-31). Values are the "All values" column of the register (pp. 62-63, B.2.5); "no alternative is deleted; every value ... remains selectable" (p. 62). Two scenarios are always in the set: the plan's recommended defaults (still PENDING OWNER) and the delegated defaults (`decisions/conflict_defaults.json`, a project decision of 2026-11-11, not the plan's).
- **S\*** (the scan set). The assignment of values to conflicts is expanded as the full Cartesian product inside each interaction group (conflicts that reach a common unit, event, object or channel; `layer.meta.linkedConflicts` and the ledger's gate chains give the groups) and independently across groups. The runner emits the group structure and the argument that the checked property factors over groups. S* also contains the two extremal scenarios (every conflict at its earliest value, every conflict at its latest) and both named defaults. A property that does not factor over groups is checked on the full product. Existing tests sample seven scenarios (`history.test.mjs SCENARIOS`); that is evidence, not S* (X-23).
- **Time grid.** Every integer minute LMT of the window of U-06, plus both sides (minus one second, plus one second) of every window boundary of every event, state change, arrival, departure, sunrise, sunset, moonrise, moonset and light-source start or end. "Every time" in a gate text means this grid. Rows without a clock minute (295 `phrase_only` and 1 `no_date` in `timeline_windows.jsonl`) are tested on the bounds of their date or part-of-day window and on three seeded interior times (A-18).
- **Entity classes.** Soldiers (officers, colour bearers, musicians, stretcher bearers), horses (ridden, led, draught), guns, limbers, caissons, wagons, ambulances, forge and battery wagon, flags and guidons, casualties on the ground, hospital contents, effects and sounds caused by a unit's actions. A gate that says "no entity" or "every unit" covers all of them in one scan.

### Q01 Unit counts and strengths match the verified OOB table

**Text (p. 136, Q).** "Unit counts and strengths match the verified OOB table."
**Definition.** O.1 (p. 135): ingest the order of battle from the Official Records and Busey and Martin, cross-checked with the NPS and Wikipedia lists; "verify every regiment, battery and troop; commander; brigade assignment; and strength"; the coverage test compares unit counts and strengths in the history layer with the verified OOB (Gate Q01); cavalry and horse artillery are first-class units. N (p. 135): carry ranges and sources for every count, never collapse a range without a decision-log entry; soldiers are instanced one-to-one up to the strength figure with no capping. B.1 (p. 9): "Any "number of soldiers to animate" must therefore be a range with a declared basis." K.1 (p. 135): a kit manifest for every regiment, battery, troop and company-level unit including cavalry, horse artillery, engineers, signal, provost, ambulance, ordnance, headquarters and medical staff. ### Q04 Arrival check

**Text (p. 136, Q).** "Arrival check. No entity of a unit exists in the scene before its arrival window opens; scan every frame range of every scenario."
**Definition.** O.2 (pp. 135-136): "No unit, soldier, horse, gun, wagon or flag of a unit appears in the scene before its arrival window opens. Ranges are carried: a unit is not shown before the earliest documented arrival time unless an owner decision chooses another scenario." Units whose arrival is unrecorded get an inferred window from their documented march, with a register entry; before arrival the unit may exist only as an approaching column on the road network at the correct place and time. The day-2 arrivals (V Corps, parts of III and VI Corps, Longstreet's divisions, Stuart's cavalry on the evening of July 2) are absent before then; the B.2.4 ledger is "the arrival source of truth; conflicts are scenarios". B.2.5 gating rules (p. 63): never-on-field units are not drawn; Stuart's brigades gated to the evening of July 2 (Hampton's rear guard and Hunterstown exempt); Pickett to the morning of July 3.
- **Q04.1 Absolute invariant.** In every scenario of S*, presence is zero for every entity class (1.5) of unit u at every grid time earlier than the minimum over all documented values of u's arrival window.
- **Q04.2 Scenario-local invariant.** Presence in scenario s is zero before the arrival window start that s selects (A-35).
- **Q04.3 Entry.** The first presence of a unit is an approaching column that enters the loaded ground at the road and time its route gives, not a deployed unit.
- **Q04.4 Departure.** After a documented departure the unit leaves by a march or is replaced by its dead and wounded where documented; an entity never vanishes.
- **Q04.5 Unknown arrivals.** Not earlier than the next documented event that requires the unit; tier inferred; register entry.
- **Q04.6 Named cases.** V Corps, II Corps, Longstreet, Stuart's brigades, Pickett, the VI Corps; units never or partly on the field.
- **Q04.7 Effects.** A sound, shot, smoke or casualty caused by a unit's action does not exist before the unit's arrival.

**Item and per-item pass rule.** Item (unit, scenario) with the entity classes inside; granularity may be (unit, entity class, scenario) where a class fails. PASS iff presence is zero for every class at every grid time before the earliest documented arrival (Q04.1) and before the scenario's own window (Q04.2), and Q04.3 to Q04.7 hold. ## 5. The rule for `source_status`

`source_status` states how well the evidence behind an S-R's claim has been checked. It is written only by `apply_passes.py` from the latest valid run records, never by hand, and each change is appended to `gate_results/status_log.jsonl` with the run id. It moves up only on a record whose evidence the runner re-matched in that run and moves down at once when an input hash changes (regression).

| Status | Meaning | May the S-R pass? |
|---|---|---|
| `seeded_unverified` | Text and tier come from the plan; no primary check (CLAUDE.md: timeline rows stay `seeded_unverified` until checked against a primary source). | No |
| `verified_primary` | A non-lead source (tier 1 to 3 of p. 134, E.1) supports exactly the claim; a short verbatim extract (under 15 words) was re-matched by the runner in the stored source text at the cited page or span; every number of the claim appears in the span; the independence class is computed (Q19). | Yes, for effective tier `documented` |
| `verified_inferred` | Effective tier `inferred`: a `reasoning` chain is recorded and every premise is itself `verified_primary` (App. B). | Yes, for effective tier `inferred` |
| `procedural_registered` | Effective tier `plausible-procedural`: a complete `procedural` block (generator and version, seed, distribution, documented context, substitute), an open L3 register entry and a recorded exhaustive search of the acquired library for the gap (Law cl. 3a). | Yes, for effective tier `plausible-procedural` |
| `partially_verified` | Some component claims verified, others not. Rows cannot be split or reworded, so the unverified part is re-tiered by a correction record; until then the row cannot pass. | No |
| `gap_registered` | The content is an open gap with a register entry (no behaviour generated, a marker shown). | No |
| `failed_lookup` | A lookup was performed and failed; recorded with host, locator, date and response. | No |
| `claim_unsupported` | The source was read and does not support the claim, or the recheck of the extract failed (`recheck_failed`). The tier must be revised. | No |
| `lead_only` | Only lead sources support the claim (Wikipedia, forum, blog, auction page). The tier cannot be `documented`. | No |
| `owner_stated` | OA rows only: the text is the owner's own instruction, not a historical claim; no source applies. | Only through the derived gate (3.1) |

**Derivation order for a row** (the first that applies): (1) a correction record in `timeline_corrections/` or `evidence_corrections/` whose citation quotes the runner re-matched in this run: verdict `confirmed` gives `verified_primary` (documented) or `verified_inferred`; `corrected` gives the same for the corrected claim, which then replaces the printed claim as what the realization record quotes; `partially_supported` gives `partially_verified`; `unsupported` gives `claim_unsupported`; `gap` gives `gap_registered`; a quote that no longer re-matches gives `claim_unsupported` with `recheck_failed`. (2) `timeline_verified.jsonl` `status_effective` through the mapping below, only after the runner re-matches `citation` and `passage_ref`. (3) otherwise `seeded_unverified`. A run that cannot re-match because the source text is not on the machine records NOT-RUN for the extract and leaves `passes` false until a run can.

| Existing value | Candidate status (the runner re-checks, U-12) |
|---|---|
| `timeline_verified.jsonl` `verified_against_or_text` | `verified_primary` (documented rows) or `verified_inferred` (inferred rows with premises) |
| `partially_verified` | `partially_verified` |
| `gap` | `gap_registered` |
| `inferred` | `verified_inferred` only if reasoning and premises are recorded, else `partially_verified` |
| `failed_lookup` | `failed_lookup` |
| `claim_unsupported_by_or_text`, `recheck_failed` | `claim_unsupported` |
| `subreq_links.json` `status`: `verified`, `gap`, `inferred`, `failed_lookup` | same mapping; the row's own note says "Evidence link only. passes stays false until the gate is run" |
| `structures/state_schedule.json` `claim_support_verified: true` | `verified_primary` after the re-match |
| `weak_source: true` with no non-weak key | `lead_only` |

**Class rules.** TL, EP, SS, WK, GE, PE, CF: as above and per class (a row's status is the weakest status of the components its class rule requires). CT: `verified_primary` when the library record carries hashes, acquisition date, rights and tier and the catalogue facts of the item (title, publisher, locator) were re-checked against the ingested source; a `blocked` item is `failed_lookup` with its record; `scheduled` is `gap_registered`. TOP: the weakest status of its children in the order `seeded_unverified` < `lead_only` < `claim_unsupported` < `failed_lookup` < `gap_registered` < `partially_verified` < `procedural_registered` < `verified_inferred` < `verified_primary`; a top row with a missing population is `seeded_unverified`. OA: `owner_stated`. `check_governance.py` keeps refusing `passes=true` on a PDF row with `seeded_unverified`; the protocol adds the refusals of 1.6.

## 6. The visual realization record that Q17 expects

The record format is owned by the realization workstream (`tools/bt/realize/README.md`, harness id `bt-realize-1`, files `GOVERNANCE/realizations/<shard>.jsonl`, 21 harness tests in `tests/governance/realize.test.mjs`). `GATE-SPEC-A.md` 3.1 left the format open and said what a record must be able to give; the harness README says that if this file defines the record differently, this file governs. This section adopts the harness format as the record, states what counts as realizing a row with the plan's citations, states when a record is valid, and lists the differences (6.8).

### 6.1 What the plan says

Q17 (p. 136): "Coverage: every timeline row has a visual realization or an open register entry." The same words are the test of O7 in D.2 (p. 124: "Coverage matrix: every timeline row either has a visual realization or a register entry. The notes did not reach minute-level everywhere. Fine grain exists for some events; coarse grain elsewhere is labeled."). Coverage map O7 (p. 5): "No gap larger than a stated interval without a labeled procedural fill". How a row is consumed (p. 9, B.2): each event row is a node with a window `[earliest, latest]`, a canonical time, a tier and a unit list; "a unit never appears before its first row, and never in two places at once"; environment rows are a separate track on the same clock; nodes with tier open gap "generate no behaviour and surface as map markers in the evidence layer"; plausible-procedural nodes "generate seeded fallback behaviour that is always visibly flagged"; where two sources disagree the canonical time is the midpoint of the documented range unless a primary report by the participant exists (an engine rule, not a historical claim). Epilogue rows are timeline rows (p. 117, B.12.2). The timeline's own interface (p. 137, T.3 and U: a timeline bar with the B.2 event markers, jump to any timeline event) exists for every row; it is the list the realization is measured against, not the realization (X-05).

### 6.2 What counts as realizing a row

A row is **realized** when, at a minute inside the time the row allows, in every scenario of the row's conflict group, what the product shows is what the row says. The record kinds (the `kind` field), the assertions that must hold and the plan citation for each:

| Kind | The row says | What must hold in the product (assertion types of the harness) | Class | Plan citation |
|---|---|---|---|---|

| `unit_activity` | units hold, fire, rest, camp, build or stand at a place | `unit_activity` (`march double_quick halt stand rest fire serve_guns gallop build_works camp`), `unit_formation`, `unit_present`, `unit_figures`, and `unit_at` a named place (or `place_unspecified` with its reason) | scene (K1) | R17 (p. 133): "Every unit shows what it was actually doing at each time"; O.4 (p. 136) an activity and a position region per unit-time slot |

### 6.4 When a record is valid

A record is valid for Q17 (an item PASS) only if all of V1 to V10 hold in the run:
- **V1 Form.** One record per row; `harness` equals the harness in use; the static validation of `schema.mjs` passes; the result is recomputed (a stored `result` that differs is `stale_result` and is ignored).
- **V2 Binding to the row.** Every unit, place and structure is bound to the row's own words (a unit by its designator or its commander's surname, a place by a gazetteer name printed in the row, a structure by a distinctive word) or declared with `via`, verbatim words of the row. A declared binding is valid for Q17 and is listed in the evidence; the S-R `passes` needs its review record in `gate_results/review_log.jsonl` (row id, binding, run id of the fresh-context verification, verdict) (U-11). An unknown or ambiguous place is listed, never guessed.
- **V3 Quote.** `claim.quote` occurs in the row's words (case, apostrophes and quotation marks folded); numbers in an assertion occur in its own quote.
- **V4 Window.** The realized interval lies inside the allowed window of the row: the whole printed cell as `timeline.mjs` reads it, a printed clock time or range widened by 20 minutes at each end (the plan's own carried clock uncertainty, p. 9; DD-RZ-02), a phrase given its part of the day (morning before noon, afternoon noon to civil dusk 20:04, evening from 18:00, NIGHT civil dusk to civil dawn 04:03, DD-RZ-02), a machine-readable window of a correction replacing it; the record says when it used the widening (`clock_tolerance_used`). Q04, Q05 and Q06 never use the widening.
- **V5 Checks hold at every minute.** Every whole minute of a span is evaluated (mode `all`) or some whole minute (mode `any`), as the assertion type defines; tolerances are the stated ones (distance: the place's own uncertainty by kind of place and, for a mapped line, its positional error plus 20 m, DD-RZ-01; time: 20 minutes); a record may tighten a tolerance and can never widen it (`tolerance_wider_than_stated`).
- **V6 Scenarios.** The record holds in every scenario of the row's group: the conflicts the row's text names and those that reach its units through their gate chains (`layer.meta.linkedConflicts`). The `scenario` field is a minimum, not a limit: the gate runner evaluates the checks in every scenario of the group through the harness library (`query.mjs`, `checks.mjs`) and records which scenarios were run.
- **V7 Completeness.** The record covers everything the row says that a picture can show. A formation is realized by its leaf units on the field: every leaf the layer lists must be drawn and satisfy the check (`quantifier: all`, DD-RZ-03); `any` only where the row says "part of". A row that says more than the product shows is not realized even if one part is (the harness's `partial`; T1-015).
- **V8 NIGHT.** A NIGHT row has a `sky` assertion with `exposure_min` and Q10 passes at the frames of the realized interval.
- **V9 Not a card alone** (6.2).
- **V10 `not_realized` records** are valid as records of what is missing only if their probe fails with the declared codes (`missing.verified`); a probe that passes means the row is shown now and the record must be rewritten (`missing.stale` is an error).
The record is valid while `harness_digest` and `inputs_digest` of `RESULTS.json` equal the current digests; the evidence status of the row (TL-3) is not a condition of validity and is judged separately.

### 6.5 The row result, and what else a row needs to pass

Q17 item for a row: **PASS** iff a valid scene-class record exists (V1 to V10); **COVERED** iff not PASS and an L3 entry exists (with the visible gap marker for an open-gap row); **FAIL** otherwise. The S-R passes only with TL-3 to TL-8 and TL-9 (4.1). The harness's `q17.ok` (a card counts) and its `register_open` (any entry that is not closed) are not used; `q17.ok_strict` is the base and the L3 test is computed by the gate runner (X-05, X-06).

### 6.6 What the harness does not do, and who does

Q17.4 (an activity and a position region with uncertainty for every unit at every grid time between arrival and departure) and Q17.5 (a gap marker in the evidence layer for every open-gap row) scan the whole product: the gate runner (`q17_coverage.py` with a node child). TL-3 (evidence status), TL-5 (scrub per row, Q12), TL-6 (Q04, Q05, Q06 on the realized content), TL-7 (Q23, Q19) and Q10 for NIGHT rows are the gate runner's; the harness gives `tier`, `status` and the units and times of each check (`spec_view`) so they run over exactly the content a row realizes. Infantry has no `fire` activity in the picture today (the layer names none; only the dismounted cavalry of ws10 does, with `picture: true`): a row that says a regiment fires cannot be realized until the layer names it.

### 6.7 Epilogue rows

The 14 epilogue rows are Q17 items (705 rows in all). The chapter's drawn content (crowd, platform, Lincoln figure, the S-080..S-088 states, sky) is checked with the scene kinds (`unit_*` for the crowd and parties, `structure_state` for WS-080..WS-088, `weather_sky`); an `epilogue` record that only shows a text card is a card.

### 6.8 Differences from the harness README (request note)

The harness needs no change to feed this gate. The differences, all applied by the gate runner on top of `RESULTS.json`, are: (1) `q17.ok` is not used; `q17.ok_strict` is the base and coverage by register means an L3 entry, not any entry that is not closed; (2) the scenario group is computed from the row's units as well as from its text (V6), so the runner re-evaluates records through the harness library; (3) declared bindings need a review record before `passes`; (4) `clock_tolerance_used` is reported in the evidence (the harness may add it to `RESULTS.json` rows; until then the runner derives it from the allowed window); (5) V7 treats `partial` as not realized for PASS. The note is `GOVERNANCE/horde/requests/bt-gates-realizations-q17-rules.md`.
