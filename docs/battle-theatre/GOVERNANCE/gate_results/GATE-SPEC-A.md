What this file is: the definition a runner must implement and a reviewer must apply. It sets no `passes` flag, runs no gate, edits no data and lowers nothing. A number quoted here was read from a named page or file. Where the plan gives no number the file says `the plan gives no figure` and marks anything it adopts as ADOPTED-PROVISIONAL, or RECORDED once a delegated decision carries it, and gives the reason; it is never presented as the plan's. **Quotation convention (checked by script, section 11.3):** a string between straight double quotation marks is a quotation of the plan and was matched against the page it is cited to; text taken from a repository file, the owner's chat or a decision is written between backticks; a paraphrase carries no quotation marks.

**Ambiguity rule.** Where the text can be read two ways, this file takes the reading under which fewer items can reach PASS (the stricter reading) and lists the ambiguity in section 8 as A-nn. The looser reading is never used silently.

**Key rulings in one place** (grounds in sections 1 and 8):
1. `passes=true` needs every applicable gate of the sub-requirement to give PASS and the class rule of section 3 to hold; a gate verdict of PASS is necessary and never sufficient (U-01, A-02).
2. A link to an open register entry is never a pass. A non-passing sub-requirement is LINKED, or LINKED-ACTIVE when its entry is complete, marked in the product, backed by a dated search of the acquired library and implemented as a reconstruction (L3); Q18 counts PASSING or LINKED-ACTIVE for a leaf row and COVERED-BY-CHILDREN for a top-level row (1.5, U-04, A-03, A-05).
3. A tier is only as high as its evidence status allows: `documented` needs a non-lead source whose short extract the runner re-matches at run time; open-gap content, failed lookups, unsupported claims and lead-only support never pass (1.3, U-02).
4. Each state-schedule row is judged by the gates of every object it names; an object no gate covers (a road, a cemetery ground) blocks the row; an empty domain is never a pass (2.4, U-03).
5. A top-level `.0000` row is covered when every child (the other rows of its requirement, the populations of 2.3 and its requirement-level check items RC-Rnn.k of section 5, 71 in all) is PASSING or LINKED-ACTIVE, and it passes only when its gates, its RC items and every child pass; R03.0000 never passes. Coverage is derived from the children and never from the row's own link or `passes`, and Q18 runs on statuses before any top row's `passes` is computed, so the rule has no cycle (3.9, 1.9, A-40).
6. A threshold the plan does not give is either an existing value adopted as a floor under a recorded delegated decision (DD-G01 to DD-G05, DD-G10, DD-G13) or UNSET, and an unset one makes the gate INCOMPLETE (1.8, section 7).
7. Anything that needs the real GPU, a listener, the owner's caps or a purchase is NOT-RUN or INCOMPLETE here, listed as owed, never claimed (U-10, U-16).
8. COVERED has a narrow reach: it counts toward a gate verdict only where the gate's own words give a register or flag branch (Q07, Q08, Q17, Q19, Q25, Q28). Where an item of Q05, Q09 or Q14 rests on a register entry it is reported COVERED and keeps the gate INCOMPLETE (1.1, A-32, A-46, A-47).
9. "Every" means every: night frames at every night minute, arrival scans over every scenario and every frame range, scrub seeks over the whole window. A sample or a finished fraction never gives PASS, a gate must be able to fail, and a skipped test is NOT-RUN (U-25, U-26, U-27, A-16).

## 1. Common machinery

### 1.1 Terms

| Term | Definition |
|---|---|
| Item | The smallest thing one gate judges: a unit in a scenario, a timeline row, one state change of one object, a datum, a night frame region. Each gate in section 4 names its item. |
| Sub-requirement (S-R) | A row of `requirements.json` `sub_requirements` (969 rows on 2026-11-14: 957 `origin: pdf`, 12 `origin: owner_chat`; there were 966 and 9 before OA10 to OA12 were added on 2026-11-13). Its text is never edited (p. 134, F: "you may never delete or reword one"). |
| Item result | One of PASS, COVERED, FAIL, NOT-RUN, BLOCKED-INPUT, N/A (table below). |
| Gate verdict | PASS, FAIL or INCOMPLETE for a whole gate (table below). |
| Link level | L0 to L3: how far a sub-requirement is tied to an open Evidence-Gap Register entry (1.5). |
| S-R status | PASSING, LINKED-ACTIVE, LINKED, UNLINKED (1.5). |
| Evidence status | The state of the underlying row's evidence: the vocabulary of `source_status` (1.3). |
| Effective tier | The tier the product may show for a row or datum after the correction overlay (1.4). |
| Scenario set S* | Every selectable combination of source-conflict values that can reach an item (1.6). |
| Renderer class | `node`, `python`, `swgl` (software GL) or `gpu` (the owner's GPU) (U-10). |

**Item results.**

| Result | Meaning |
|---|---|
| PASS | The property holds for this item and a run record names the evidence. |
| COVERED | The item does not meet the PASS branch, but the gate's own text provides a register or flag branch and that branch is fully met. The branches are those of Q07 ("or is flagged with an open register entry"), Q08 ("or are flagged"), Q17 ("or an open register entry"), Q19 ("or a flag"), Q25 ("blocked with register entry, or scheduled with a reason") and Q28 ("otherwise marked reconstruction in the viewer"). Counts toward a gate verdict only for those six gates; never toward `passes`. For a gate whose text has no such branch (Q05, Q09, Q14) an item that rests on a register entry is reported COVERED and keeps the verdict INCOMPLETE (A-32, A-46, A-47). |
| FAIL | The property is violated (an entity before its arrival window, a modern object in the scene, an unmarked procedural item, a missing datum). |
| NOT-RUN | The check could not be executed in the available environment (real GPU, missing tool, host blocked). The record states why. Non-passing. |
| BLOCKED-INPUT | An input the gate names does not exist or is not eligible (no documented camera position, no verified OOB table, no cap set). Non-passing. No vacuous pass (U-03). |
| N/A | The gate's domain excludes the item. N/A never satisfies an item whose every listed gate is N/A (U-03). |

**Gate verdict.** PASS: at least one in-domain item exists, every in-domain item is PASS (or COVERED where the gate text allows it), and no item is FAIL, NOT-RUN or BLOCKED-INPUT. FAIL: at least one FAIL. INCOMPLETE: no FAIL, but at least one NOT-RUN or BLOCKED-INPUT, a COVERED item in a gate whose text has no register or flag branch (Q05, Q09, Q14), a threshold that is not recorded, a run that finished only a fraction of its grid (U-26), or an empty domain.

### 1.2 Universal rules (apply to every gate and every class)

Each rule cites the text it comes from.

- **U-01 Gate-pass is necessary, not sufficient.** "A sub-requirement passes only when its gate passes" (p. 136, Q). `passes=true` needs all of: (a) every applicable gate in `gate_ids` gives item result PASS for this sub-requirement's items (A-02); (b) the class rule of section 3; (c) P2 to P6 of U-02. `gate_ids` with several gates is a conjunction.
- **U-02 What PASS means for a sub-requirement.** P1 item results PASS under (a). P2 evidence sufficiency: the tier the product shows does not exceed the evidence status (1.3, 1.4). P3 marking: every non-documented content of the item is marked (Q23 item PASS). P4 conflicts: every source conflict that reaches the item is carried as a selectable scenario and the item passes in each (A-06). P5 no content gap: an item whose own content is an open gap, a failed lookup, an unsupported claim or lead-only support never passes. P6 provenance of the run: command, versions, input hashes, renderer class and date are recorded (1.7), and any renderer-dependent part marked owed on the GPU is listed as owed.
- **U-03 No vacuous pass.** An empty domain gives BLOCKED-INPUT, never PASS. An S-R whose every listed gate is N/A for it cannot pass by that; it needs the domain gate of 2.4 to pass, otherwise it stays LINKED.
- **U-04 Linked is not passing.** Q18 says each sub-requirement is "passing or linked to an open register entry with an active reconstruction" (p. 136, Q18); F says "100% of sub-requirements are either passing or linked to an open register entry awaiting an owner decision with work continuing on the best reconstruction" (p. 134, F); Z.1 says "every in-scope sub-requirement passes or is linked to an open register entry with an active reconstruction" (p. 138, Z). Passing and linked are two different states. A link never turns a FAIL, NOT-RUN or COVERED item into PASS (A-03).
- **U-05 No lowering, no skipping.** "Never lower a threshold to pass" (p. 136, Q). A gate, threshold, scenario, row or class is never narrowed, disabled or skipped to make an item pass (p. 138, Z "lowering a threshold to pass"; Law cl. 1, 8).
- **U-06 Scope of time.** The whole window: 1863-06-26 00:00 through 1863-07-14 23:59 local mean time (LMT = UTC minus 5 h 09 min, p. 111, B.10.2), plus the epilogue days 1863-11-18 and 1863-11-19. The start is June 26 (p. 136, O.3), the end is the owner's chosen end, the notes covering the retreat through about July 14 (p. 137, T.4), and the epilogue is R22 (p. 133, A; pp. 116-117, B.12). Narrowing is an owner decision (p. 130, D.8.2 item 2; DD-20 keeps the full window). All three days and all nights are in scope (p. 138, Y.12).
- **U-07 Scope of scenarios.** Every check that depends on a source conflict is run over S* (1.6). "Scan every frame range of every scenario" (p. 136, Q04).
- **U-08 Evidence.** A datum is `documented` only with a non-lead source that states exactly it and a short extract (p. 134, E.2; p. 136, P.3; App. B p. 139). Wikipedia, forums, blogs, auction listings and wikis are leads (p. 134, E.1, E.2, E.7). A quotation is at most under 15 words (p. 134, E.6; App. B).
- **U-09 Never fabricate.** No invented quotation, measurement, name, time, number, citation or URL; a failed lookup is recorded as failed (p. 132, Law cl. 4). A gate result never contains an extract the runner did not match in the stored source text.
- **U-10 Renderer class.** A node or python result cannot certify a property defined on the picture. A software-GL (`swgl`) picture result is valid for properties that do not depend on the GPU (pixel statistics of a deterministic shader, draw-list contents, pixel identity between two runs) and is recorded as `PASS@swgl` with `real-GPU confirmation owed`. Frame time, GPU memory and the real-GPU baseline need `gpu`; the runner records NOT-RUN with the reason (the container has no GPU). A visual result is claimed only for frames that were looked at.
- **U-11 Independent verification.** A fresh-context verification run per milestone, told to flag only correctness and requirement gaps (p. 136, Q, last paragraph; p. 137, X.5). "Do not self-certify what you have not run" (p. 136, Q). The record of that run is part of the milestone (Q27.5).
- **U-12 Records decide.** `passes` is a pure function of the latest valid run records (1.7). A record expires when an input hash it names changes. A failing or missing record sets `passes=false`.
- **U-13 Where the record or physics makes literal compliance impossible** the item is not exempt (Law cl. 3, 5): the strongest evidence-based reconstruction is built, registered (tier, marking, owner question), marked in the product and escalated (Law cl. 3 a-d, p. 132). The item is then at most LINKED-ACTIVE.
- **U-14 Visible gaps.** A missing-evidence item is shown as a marked gap (Law cl. 7, p. 132; p. 9, B.2: "open gap ... generate no behaviour and surface as map markers"). A concealed gap is a violation: FAIL for Q23.
- **U-15 Reading the product.** Gates test what the page loads and draws (the shipped data, the draw lists, the audio graph), not only the source data. The history layer is read-only to renderers (p. 134, D).
- **U-16 Owner-only acts.** A gate that needs an account, licence acceptance, payment, third-party contact, deployment or a cap value (D.8, p. 130) is INCOMPLETE with the exact owner step written next to it. Claude never performs the act (p. 132, Law cl. 2; standing constraints in CLAUDE.md).
- **U-17 Delegated defaults.** The owner delegated the default view of conflicts on 2026-11-11 (the header of the delegated decisions). A default chosen under that delegation is the default for Q02, Q19 and class CF only while (a) it is recorded as the entry C-nnn of section A of the delegated decisions (called DD-C-nnn in this file) and as `conflicts.C-nnn.default_scenario_id` in `decisions/conflict_defaults.json`, (b) the product labels it `Default chosen under delegated authority, reversible by the owner` with its tier, (c) the plan's default and every other value stay selectable. The word DECIDED is never written to `decision_log.md` for it.
- **U-18 Clocks.** All times are LMT as printed. The roughly 20-minute Union and Confederate clock difference "is not applied to any row, it is carried as uncertainty" (p. 9, B.2). Nothing in a gate applies it: Q04, Q05 and Q06 are exact, and so is the match of a realization record to the time its row allows, which has no margin at either end of a printed clock time (DD-G09). A wider window that another tool uses as its own necessary condition is not adopted by a gate.
- **U-19 Row identity.** Day-header rows of the timeline are not events (p. 9, B.2) and are not sub-requirements. Row ids T1-001.., T2-001.., T3-001.. (T3-131 absent) and E-001..E-014 are stable (p. 9).
- **U-20 Thresholds.** Section 1.8: only recorded thresholds are used; an unrecorded one makes the gate INCOMPLETE.
- **U-21 Fresh state.** A run starts from the committed inputs plus the working-tree data it names by hash; it never reads a result file as if it were an input (GATE-SPEC-B 5.4).
- **U-22 Heavy runs** go through `tools/horde/bench.sh` (at most two heavy jobs, timing runs alone). A run that was waiting for the lock is not a failure.
- **U-23 Copy audit.** Gate outputs under `GOVERNANCE` are not shipped. A gate assertion that reads shipped files (Q23, Q02) never writes or quotes how the site was produced into shipped files (FINAL-ACCEPTANCE copy audit; DEC-006).
- **U-24 Product marking after DEC-006.** The "reviewed by automated subagents" label is dropped (DEC-006). Tier marking of non-documented content stays (Q23), as does the register (CLAUDE.md).
- **U-25 A gate can fail.** Every check Qnn.k has at least one negative control: an injected defect that the runner must report as FAIL (a unit placed before its arrival window, a fence that never changes state, an unmarked procedural item, a quotation that is not in the source text), run in the same suite as the runner. A runner without one is not accepted as a gate (p. 136, Q: "Do not self-certify what you have not run"; p. 138, Z forbids "marking a sub-requirement as passing without running its gate").
- **U-26 Exhaustive or incomplete.** "Every", "at every" and "scan every" in a gate text mean the whole domain and the whole grid of 1.6 (p. 136: Q04 "scan every frame range of every scenario", Q10 "At every night time", Q22 "at every time"; Law cl. 1 forbids skipping "a minute of the timeline", p. 132). A run that completes a fraction records the fraction and the verdict is INCOMPLETE; a sample, a spot check or a coarser grid never gives PASS. Work may be chunked and resumed, with results cached by a content hash of inputs, scenario, time and view.
- **U-27 Skipped is not passed.** A test or spec that is skipped, or that prints a NOT RUN line, counts as NOT-RUN for the part it names (p. 138, Z forbids "skipping an arrival check, night check, fence or earthwork state-change check or scrub test").
- **U-28 Existing greens are evidence, not results.** An existing self-check or suite (`check_structures.py`, the node suite, the browser specs) validates data and engine consistency. Its output is an input to an item and never a gate result (U-21).

### 1.3 Evidence statuses: the vocabulary of `source_status`

`source_status` currently holds one value, `seeded_unverified`, on all 969 rows, and `check_governance.py` refuses `passes=true` on a PDF row that still has it. The lifecycle below is the vocabulary gate scripts write (only gate scripts, never by hand; each change is logged with the run id).

| Status | Meaning | May the S-R pass? |
|---|---|---|
| `seeded_unverified` | Text and tier come from the PDF; no primary check yet (CLAUDE.md: Timeline rows are `seeded_unverified` until checked against a primary source). | No |
| `verified_primary` | A non-lead source (tier 1 to 3 of p. 134, E.1) supports exactly the claim; a short verbatim extract (under 15 words) was re-matched by the runner in the stored source text at the cited page or span (citation checker, p. 126, D.4.3 step 11); numbers in the claim appear in the span. | Yes, for effective tier `documented` |
| `verified_inferred` | Effective tier `inferred`: a `reasoning` chain is recorded and every premise is itself `verified_primary` (App. B, p. 139). | Yes, for effective tier `inferred` |
| `procedural_registered` | Effective tier `plausible-procedural`: complete `procedural` block (generator and version, seed, distribution, documented_context, substitute), an open register entry, and a recorded exhaustive search of the acquired library for the gap (Law cl. 3a). | Yes, for effective tier `plausible-procedural` |
| `partially_verified` | Some component claims verified, others not. Rows cannot be split or reworded, so the unverified part is re-tiered by a correction record; until then the row cannot pass. | No |
| `gap_registered` | The content is an open gap with a register entry (no behaviour generated; marker shown). | No |
| `failed_lookup` | A lookup was performed and failed; recorded with host, locator, date and response. | No |
| `claim_unsupported` | The source was read and does not support the claim, or a recheck of the extract failed (`recheck_failed`). The tier must be revised. | No |
| `lead_only` | Only lead sources support the claim (Wikipedia, forum, blog, auction page). The tier cannot be `documented`. | No |
| `owner_stated` | OA rows only: the text is the owner's own instruction, not a historical claim, so no source applies. | Only through the derived gate (3.10) |

Mapping from the vocabularies that exist today (candidates only; the gate re-checks, U-12):

| Existing value | Candidate status |
|---|---|
| `timeline_verified.jsonl` `status_effective`: `verified_against_or_text` | `verified_primary` (documented rows) or `verified_inferred` (inferred rows with premises) |
| `partially_verified` | `partially_verified` |
| `gap` | `gap_registered` |
| `inferred` | `verified_inferred` only if reasoning and premises are recorded, else `partially_verified` |
| `failed_lookup` | `failed_lookup` |
| `claim_unsupported_by_or_text`, `recheck_failed` | `claim_unsupported` |
| `subreq_links.json` `status`: `verified`, `gap`, `inferred`, `failed_lookup` | same mapping; the row's own note says `Evidence link only. passes stays false until the gate is run` |
| `structures/state_schedule.json` `claim_support_verified: true` | `verified_primary` |
| `weak_source: true` with no non-weak key | `lead_only` |

**Derivation order for a row** (the first rule that applies). (1) A correction record in `timeline_corrections/` or `evidence_corrections/` whose citation extracts the runner re-matched in this run: the verdict word gives the status, `confirmed` and `corrected` giving `verified_primary` (effective tier documented) or `verified_inferred` only when the record's `remains_unsupported` list is empty, otherwise `partially_verified` (a row cannot be split or reworded); `partially_supported` gives `partially_verified`; `unsupported` gives `claim_unsupported`; `gap` gives `gap_registered`; a lookup record that found nothing (`no_passage_found_in_saved_pages`, `no_relevant_passage_found_in_saved_pages`) gives `failed_lookup` with its host, locator, date and response; `passages_found_see_hit_pages` gives no status by itself (passages found are leads until a verdict is written); an extract that no longer re-matches gives `claim_unsupported` with `recheck_failed`; a verdict word outside this list has no effect and is reported. A `corrected` verdict replaces the printed claim by `corrected_claim` as what a realization record must quote. (2) `timeline_verified.jsonl` `status_effective` through the mapping above, only after the runner re-matches `citation` and `passage_ref`. (3) Otherwise `seeded_unverified`. A run that cannot re-match because the source text is not on the machine records NOT-RUN for the extract and leaves `passes` false until a run can. A status moves up only on a record whose evidence was re-matched in that run and moves down at once when an input hash changes.

**Several records for one row.** The two correction folders hold two kinds of record, told apart by their fields and never by file name (`spec-a-evidence/corrections_census.py`). A row-level record carries `sub_claims` (spelled `subclaims` in 77 records), `citations`, `seed`, `before`, `schedule_id` or `lookups` and no `xid`: it is the verdict on the whole row. A supplementary record carries an `xid` and one `sub_claim` (written by a lookup workstream; its verdict word is `partially_supported` or a failed-lookup word): it supports or fails to support one sub-claim and is never a verdict on the row. The status of a row follows its row-level record by the derivation above. A supplementary record can add a re-matched extract to one sub-claim and can record a failed lookup for it; it never raises the status of a row above that of its row-level record, and a row with supplementary records only is at best `partially_verified`, however many sub-claims they support (a row cannot be split or reworded). When a row has more than one row-level record the weakest verdict governs until a later record names the one it replaces (none has two today). A record of neither kind is reported and has no effect. `remains_unsupported` is a list in the timeline records and a string in the evidence records (the empty string for none): both are read, and a string that parses as a list is read as that list. Counted on 2026-11-14: `timeline_corrections/` holds 324 records over 226 row ids (173 row-level and 151 supplementary; 44 ids have more than one record; 53 ids have supplementary records only), of which 39 row-level records have the verdict `confirmed` or `corrected` and nothing left unsupported; `evidence_corrections/` holds 1,793 records over 169 ids (137 row-level and 1,656 supplementary; 73 ids have more than one record; 32 have supplementary records only), of which 70 have that verdict and nothing left unsupported. Those 39 and 70 records are the ones from which a row can reach `verified_primary` or `verified_inferred`, after the runner has re-matched their extracts.

**Records whose id is a top-level row.** 1,344 of the 1,793 evidence records carry the id of a top-level row (R02.0000 633, R13.0000 341, R20.0000 277, R14.0000 46, R05.0000 39, R15.0000 7, R22.0000 1), 1,329 of them Park Service landscape-report statements about fences, fields, woodlots, buildings and ground, 13 newspaper statements, and two requirement-level records of shards (R13.0000, R14.0000). They are claims about the requirement as a whole. They are not evidence for the aggregation text of the row and give a top row no status: a top row is covered only through its children (3.9 TOP-1). They are the evidence from which the populations of 2.3 (one per structure, per vegetation polygon class and so on) are to be generated; the runner counts them per requirement and lists them as unassigned evidence until a child row names them (A-56).

**Row-level records by class** (2026-11-14, `spec-a-evidence/check_counts.py`; clean means the verdict `confirmed` or `corrected` with nothing left unsupported, which is the most that can reach a verified status once the extracts are re-matched and the class rule holds): timeline 173 of 691 rows (39 clean); R14.S 88 of 88 (42 clean); R14.E 18 of 18 (9 clean); R13.G 16 of 18 (10 clean); R13.P 9 of 14 (8 clean); R12 catalogue 4 of 45 (1 clean); R03.C 0 of 47; R22 epilogue 0 of 14. Supplementary records only: R13.P 3, R12 5, R03.C 5, R22 14. No record at all: R13.G 2, R13.P 2, R12 36, R03.C 42.

### 1.4 Tiers (App. B, p. 139) and the effective tier

- `documented`: at least one non-lead source with a short extract; the claim matches the source. `inferred`: `reasoning` required. `plausible-procedural`: `procedural` block required, and a register entry when the gap affects a requirement. Items affecting a visible result need two sources with distinct `independent_of` roots or a flag. `render_flag`: 0 documented, 1 inferred, 2 plausible-procedural. Every structure or vegetation state change carries a `state_schedule`; every kit item carries `validity` dates.
- "Open gaps are not a tier: they are register entries" (p. 133, B). The timeline uses the category `open gap` for rows (p. 9, B.2). It is shown as a marked gap, not as content.
- C.10 (p. 121): substitute content (modern motion bases, synthesized audio, open textures) is recorded in the asset manifest with licence, source and method and "never receives a documented tier".
- **Effective tier** of a timeline row or datum, in order of precedence: (1) an accepted correction record (`timeline_corrections/`, `evidence_corrections/`) with a citation and passage; (2) `timeline_verified.jsonl` `tier` as adopted by DD-08 and DD-09; (3) the seed tier (`timeline_seed.jsonl`, never rewritten). The effective tier can only be lower than or equal to what the evidence status allows (U-02 P2). Promotion needs a matched citation. A demotion is always allowed. The overlay also holds the value `unclassified` for five rows (T2-121, T2-133, T2-148, T2-176, T2-178; all `status_effective` gap): it is not a tier of the plan, so such a row has no effective tier and is treated as an open gap until a correction record gives it one (TL-1, A-53).

### 1.5 Register links: "open", "active reconstruction", link levels

"Open register entry" uses the status vocabulary of Appendix A (p. 138): `open`, `awaiting owner`, `decided`, `closed`. A sub-requirement's link counts only for `open` and `awaiting owner` (A-04). A `decided` entry means the owner (or delegate) has chosen: the decision is implemented and the sub-requirement must then pass on its own. `closed` entries do not count (two exist today: EG-0007, EG-0025). Entries are never deleted (p. 137, R).

| Level | Condition (all runner-checkable) |
|---|---|
| L0 UNLINKED | No `register_ids` entry with status `open` or `awaiting owner`. This is "unfinished work, not an exception" (p. 134, F). |
| L1 LINKED-RECORD | At least one open entry whose fields are all present and non-placeholder: `title, rids, cat, desc, why, searched, subst, recon, tier, marking, status` plus the owner-decision field `owner_q` (p. 138, Z.3: "a reconstruction, a marking and an owner-decision field"). A placeholder is a value that is empty, `-`, `none`, `n/a` or the marker `not stated by the shard proposal`. |
| L2 LINKED-MARKED | L1, and the marking is in the product for this item (Q23 item PASS for the item; for a gap, the visible gap marker with its register link). |
| L3 LINKED-ACTIVE | L2, and (b) the entry carries a dated machine-readable search log: a sidecar `GOVERNANCE/register/search_logs/<EG id>.json`, a list of `{source_id, locator, date_searched, result, note}` with `result` one of found, negative or unreachable, naming the acquired sources that could settle the gap, each searched on or after the date that source was acquired (Law cl. 3a: "exhausting the free primary-source library" ... "before settling for less"); and (c) the reconstruction named in `recon` is present in the product build for this item (a datum, draw object, scenario or realization record that lists the register id in its `register_ids` and is loaded by the page), or, where the reconstruction is `show a marked gap, generate no behaviour`, the marker object exists. |

### 1.6 Scenario space, time grid, entity classes

- **Scenario.** A function from every conflict C-001..C-047 (and the further conflicts the plan prints elsewhere, A-31) to one of its values: the "All values" column of the register (pp. 62-63, B.2.5). Two scenarios are always in the set: the PDF recommended defaults (the "Recommended default" column, still PENDING OWNER) and the delegated defaults (`decisions/conflict_defaults.json`, a project decision of 2026-11-11, not the plan's). Every value stays selectable (p. 62: "no alternative is deleted; every value ... remains selectable").
- **S\*** (the scan set). The assignment of values to conflicts is expanded as the full Cartesian product inside each interaction group (conflicts that reach a common unit, event, object or channel; the product's `layer.meta.linkedConflicts` and the ledger's gate chains give the groups) and independently across groups. The runner emits the group structure and the argument that the checked property factors over groups. Additionally S\* contains the two extremal scenarios (every conflict at its earliest value, every conflict at its latest) and both named defaults. A property that does not factor over groups is checked on the full product.
- **Time grid.** Every integer minute LMT of the window of U-06, plus both sides (minus one second, plus one second) of every window boundary of every event, state change, arrival, departure, sunrise, sunset, moonrise, moonset and light-source start or end. "Every time" in a gate text means this grid. Rows without a clock minute (295 `phrase_only`, 1 `no_date` in `timeline_windows.jsonl`) are tested on the bounds of their date or part-of-day window and on three seeded interior times (A-18).
- **Entity classes.** Soldiers (including officers, colour bearers, musicians, stretcher bearers), horses (ridden, led, draught), guns, limbers, caissons, wagons, ambulances, forge and battery wagon, flags and guidons, casualties on the ground, hospital contents, effects and sounds caused by a unit's actions. A gate that says "no entity" or "every unit" covers all of them in one scan.

### 1.7 Result records and the `passes` protocol

A run writes one result file per gate: `GOVERNANCE/gate_results/Qnn.json` (and `OAnn.json` for a derived gate of 3.10, `RC-Rnn.json` for the requirement-level checks of section 5), authoritative and written atomically. The record it replaced is kept as `Qnn.prev.json` so that a regression can be seen. Evidence larger than 2 KB (rendered frames, long extracts) goes to `gate_results/evidence/Qnn/` and is named in the item by path and sha256. The fields below are the minimum; a runner may add fields.

```
{ "schema": "bt-gate-result/1", "gate": "Q07", "run_id": "...", "started_utc": "...", "finished_utc": "...",
  "command": "...", "renderer_class": "python|node|swgl|gpu|mixed", "runnable_here": true, "tool_versions": {...},
  "inputs": [ { "path": "...", "sha256": "..." } ],
  "thresholds": [ { "id": "T-Q10-1", "value": ..., "decision": "DD-G03" } ],
  "scenario_set": { "id": "...", "groups": [...], "count": N },
  "time_grid": { "step_s": 60, "boundaries": true, "fraction_done": 1.0 },
  "verdict": "PASS|FAIL|INCOMPLETE",
  "counts": { "PASS": 0, "COVERED": 0, "FAIL": 0, "NOT-RUN": 0, "BLOCKED-INPUT": 0, "N/A": 0 },
  "owed": [ "real-GPU confirmation: ..." ],
  "items": [ { "id": "R14.S-062/Q07.4/default", "check": "Q07.4", "pass": false,
               "result": "PASS|COVERED|FAIL|NOT-RUN|BLOCKED-INPUT|N/A", "reason": "...", "evidence": { ... },
               "sub_requirements": [ "R14.S-062" ], "register_ids": [ ... ], "looked_at": false } ] }
```

`id`, `pass`, `reason` and `evidence` are required of every item. `pass` is `true` only for the result PASS: COVERED, NOT-RUN, BLOCKED-INPUT, N/A and FAIL are all `pass: false`. A gate with `runnable_here: false` (Q15; the picture parts of Q10, Q24 and the rest when no browser is available) records the reason and its items are NOT-RUN. Two runs on the same inputs give identical `items`; timestamps and durations live in the header, and the seed of every random choice is recorded.

- A script, not a person, derives the S-R status from the latest valid records and writes `passes`, `source_status`, `register_ids` and `owner_decision_ids` in `requirements.json` as a byte-exact textual patch (other bytes unchanged, idempotent, refused when the re-parsed non-owned fields differ). It writes nothing else, and never `text`, `id`, `origin`, `gate_ids`.
- `passes` is recomputed at every run. It is true exactly when 1.2 U-01 and U-02 hold on the latest valid records for every item of the sub-requirement. A regression sets it back to false and the change is logged in `progress.md`.
- A record is valid while every input hash it names is unchanged. The runner names the data files, code files and source-text hashes it read.
- `check_governance.py` already refuses `passes=true` on `seeded_unverified` PDF rows; the protocol adds: refuse `passes=true` with no run record, with a record older than an input, or with `NOT-RUN` or `BLOCKED-INPUT` in any applicable gate.

### 1.8 Thresholds

"Never lower a threshold to pass; thresholds are set at gate creation from the vertical slice and changed only by owner decision" (p. 136, Q). The plan prints numbers only where this file cites a page for them (for example the 100 random jump times, p. 130, D.7 phase 12). For the others:

1. The threshold registry (section 7) lists each threshold id, the plan's words, the plan's figure (or "none"), the value in code today (from GATE-SPEC-B 5.1), and the value adopted.
2. A recorded threshold has a decision id (DD-Gnn in `DELEGATED-DECISIONS-2026-11-11.md`). A runner reads thresholds from `GOVERNANCE/gate_results/thresholds.json`; a threshold with no decision id makes the gate INCOMPLETE (`threshold not recorded`), never PASS.
3. A value may be tightened by recording a stricter one. It may not be loosened without a recorded owner decision.
4. Values taken from a measurement (frame time, reprojection error) are re-measured at the first run on the real GPU and the stricter of measured and recorded applies.

### 1.9 Order of evaluation (no cycle)

Statuses are computed in strata, so that no gate reads a flag that a later step writes. (1) Every gate except Q18, then the requirement-level checks RC-R01 to RC-R22 of section 5, each after the gates its items name (an RC item that names a gate reads that gate's record; none reads Q18's record or a `passes` flag). (2) The status of every leaf row (PASSING, LINKED-ACTIVE, LINKED, UNLINKED) from those records and the register. (3) The derived coverage of the 22 top rows from step 2 and the RC items (3.9 TOP-1). (4) Q18, from the statuses of steps 2 and 3 and the records of step 1, never from a `passes` flag. (5) `passes` of the leaf rows. (6) `passes` of the 22 top rows, each after all its children and after Q18, and an input to nothing. R01.0000 lists Q18 among its gates; it is not its own support, because Q18 never reads its `passes` (3.9 TOP-5, A-40).

### 11.4 Quotation convention and page checks

A string between straight double quotation marks is a quotation of the plan and is matched against the plan text; text taken from a repository file, the owner's chat or a decision is written between backticks; a paraphrase carries no quotation marks. `check_quotes.py` splits each quotation on an ellipsis, normalizes case, spacing, dashes and quotation characters, and requires every fragment of 10 or more characters on a page that the line or its heading cites (a quotation that crosses a page break is matched on the joined text with the page footers removed). A quotation found only on another page is reported as WRONG-PAGE and one found nowhere as NOT-IN-PLAN: both counts are 0 in the final run (11.3). `check_pages.py` tests every citation of the form page and section label: a Part E label must lie on a page of that section, and a label of Parts B to D must occur as text within two pages of the cited one; 0 mismatches. The checks do not reach a page or a number that is stated without a quotation or a label; those were read from the plan for revision 3 where this section says so and are otherwise those of revisions 1 and 2.
