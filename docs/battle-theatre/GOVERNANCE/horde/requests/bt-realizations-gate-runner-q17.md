# bt-realizations -> bt-gate-engine: how a gate runner reads Q17

Owner of the harness: bt-realizations (`tools/bt/realize`, README.md there). Needed from: bt-gate-engine.

**What.** `node tools/bt/realize/check.mjs` (about 3 s, node only) runs every realization record in `GOVERNANCE/realizations/<shard>.jsonl` (and `EXAMPLES.jsonl` for rows with no shard record) against the shell's own modules and writes `GOVERNANCE/realizations/RESULTS.json`. Per row (691 timeline rows in `rows`, 14 epilogue rows in `epilogue`): `realized`, `kind`, `why`, `codes`, `record`, `assertions[]`, `realization_class` (`scene` or `card`), `register_open` (the open register entries linked to the row's sub-requirement: the rule of `tools/bt/check_coverage.py`), `q17_covered`, `q17_covered_strict`, `coverage`, `spec_view` (the fields of GATE-SPEC-A 3.1 TL-2: `t_start, t_end, subjects, probe, expected, observed_ref`). `q17` holds `ok` (a row realized by a card, or only partially, counts) and `ok_strict` (such a row counts only with an open register entry too: GATE-SPEC-A TL-4, TL-11; a record lists the parts it does not show in `not_shown`). The harness sets no `passes` flag and decides neither reading (DD-RZ-04); the conservative one is `ok_strict`.

**Scenarios.** A record names its scenario (`default`, `pdf`, a `choices` object, a list, or `conflicts` = the default plus one scenario per value of every `C-nnn` the row's text names: GATE-SPEC-A TL-8). `RESULTS.json` lists the scenarios run per row.

**Not in the harness.** Q17.4 (an activity and a position region with uncertainty for every unit at every grid time between arrival and departure) and Q17.5 (a gap marker in the evidence layer for every open-gap row) scan the whole product, not rows. TL-3 (evidence status), TL-5 (scrub per row: Q12), TL-6/TL-7 (Q04, Q05, Q06, Q23 on the realized content) are the gate runner's: the harness gives `tier` and `status` per row and the units and times of each check (`spec_view`) so that they can be run over exactly the content a row realizes.

**Run.** `node tools/bt/realize/check.mjs --json` prints the report; `node --test tests/governance/realize.test.mjs` runs the harness tests (24, injected wrong records included). The format authority: GATE-SPEC-A leaves the record format to the realization workstream; if GATE-SPEC.md defines it differently, it governs and the differences go in a note.
