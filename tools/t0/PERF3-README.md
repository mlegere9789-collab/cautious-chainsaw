## Registering it and the ordering (integrator)

* `trains.json`: `"PERF3"` in `optional_groups` after `"PERF2"`; copy the three files to `tools/t0/patches/`; build with `--with ...,PERF2,PG-perf2,PERF3,PG-perf3,PG-zperf3`.
* **Order.** No find of PERF3 overlaps PERF2, POLISH, CLOCK, DATA, MON or ANIM (the bundle patch anchors on the shipped `lS`). Page groups are applied in sorted name order after the fixed groups: `PG-perf3` sorts before `PG-polish` (its seven finds are in `compare`, `viewshed` and `watch-together`, none of them a line PG-polish edits); `PG-zperf3` exists only because its one find is text that `PG-polish` writes (the `--gt-evt-h` tracker of `index.html`), so its name has to sort after `PG-polish` and `PG-polish-legal`.
* ANIM: nothing to register beyond what ANIM needs; the sliced work is on by default in the browser (`GTANIM` passes `sliceMs: 4`); `?anim=sync` gives the one-call solves back (kill switch for the sliced work only; `?anim=legacy` still switches the whole engine off). Nodes tests and the headless harness do not pass `sliceMs`, so they run as before.

## What was measured, and how

Everything below was profiled first on the stack tree (Chrome `Profiler` at 200 us, Long Animation Frames with script attribution, trace events of the renderer main thread per long task, `CSS.getPlatformFontsForNode`, `Performance.getMetrics`), phone emulation (390 x 844, touch, 4x CPU throttle like the acceptance harness), cold page loads (cache, storage and service worker cleared). The machine is shared with other agents' browsers: one run of the same page moves by a factor of two to ten, so every comparison is interleaved and repeated and a number is quoted only next to the control measured the same way (n given). The honest result is below in "Results"; what the noise hides is said where it applies.

## 1. The date-jump tap on the phone (items 2 and 3)

**A 130 ms task from a forced layout (the shipped unit routine).** `lS` (the unit canvas) read `canvas.getBoundingClientRect()` at the top of every repaint, and a repaint from a click runs right after React has committed the new tick, so the read forced the style and layout of the page inside the click handler: 66 ms of 146 at 4x CPU. `PERF3-lS-canvas-size` reads the size from the Mapbox transform instead (the canvas fills the map container; Mapbox keeps its size in `transform.width/height`, updated by its own resize observer, which also fires the move event that repaints). On the stack without ANIM the first tap in a fresh page went from one 146 ms long task (170 ms Long Animation Frame, 66 ms forced layout in the click) to one 93 ms task (106 ms, 0 forced), once (`tmp/perf3/tapprof.mjs`). Over four repeated taps after a warm-up pair (T0-P3-09) the click's forced layout is 6-24 ms on the control and 0 with the patch, but the worst long task is the same within the noise (59-89 ms with the patch, 54-104 ms on the control, two runs): the layout that the new card and clock text need is done in the frame that paints them instead of inside the click handler, it is not less work. So the patch does what was asked (no layout forced in the click; the handler's own 35-65 ms is React's commit) and does not shorten the response. The canvas still follows a resize (900 x 652 map, 900 x 652 canvases).
**The second source of forced layout**: an inline script of `index.html` (the `--gt-evt-h` tracker of the event card, from POLISH) read `getBoundingClientRect().height` of the card inside the mutation-observer callback that follows every React commit, 47 ms at 4x. `PERF3-evt-height-raf` reads it once per frame in `requestAnimationFrame` (T0-P3-08: the variable is still set when the card opens and 0 when it is closed). What is left of the tap is the browser's own style and layout of the new story card and clock text: 80 ms at 4x of which 55 ms is `InlineNode::ShapeText` of the new text; it is the work that the paint needs anyway.

**ANIM: 0.7 to 1.2 s of `requestAnimationFrame` tasks after the tap.** Not the draw and not the playing loop: the layout. A cut (the first frame, a date jump, a zoom jump) resets the layout's history and the next solve starts from clean state: every unit a tile at its true place, then merge, place, merge again until nothing overlaps. That cold solve is the most expensive thing the engine does (33 to 110 ms on a desktop for the densest scenes in node, 400+ ms of work on the 4x phone), and the rest canon starts a second cold solve (its first probe) 6 frames after the picture rests. Warm frames cost 0.1 to 2 ms, playback frames 5 ms mean at 4x. At the date jump that was one 947 ms task and one 633 ms task (the old engine, same tree: 797 and 508, 547 and 426 ms in T0-P3-04).
* **Sliced work** (`createCore({ sliceMs: 4 })`, `host/app.mjs`): the placement pass and the solve are generators with a checkpoint every eighth tile; a job runs one slice per frame (6 ms for the cold start, 4 ms for a canon probe). While a cut's cold start is pending the old marks fade out as ghosts (a cut was a cross-fade already) and the new marks are born with the same fade when the layout is warm; a new dataset (a day of placements arrives 1.5 s after the first frame) is warmed the same way while the marks stand as drawn (71 ms in one step before, at most 8 ms now, no mark vanishes). The sync solve is the same generator run to the end, so the frames are bit-identical (T0-P3-01: 8,000 frames of real data in five scenes hash to what the engine of before gave), and a sliced run ends in the same set of marks as the one-call run (T0-P3-03: 62/62, 70/70, 62/62, same sets). In node the steps of a sliced run are p95 6.2 ms, p99 7.4, max 10.4 with 4 ms + 6 ms slices (T0-P3-02), with 0 overlaps and 0 unrepresented units on every frame. `?anim=sync` gives the one-call solves back.
* **A faster solver (same frames)**: the placement search (`nearestFree`) was 40 % of the solve. A column whose blocked intervals cover what the displacement circle leaves of it is skipped at once instead of tried row by row (the failing searches, 9,000 of 32,000 calls in the six-jump benchmark, spent their time there); `Math.hypot` only where its value decides; no allocation for obstacles outside the box; no `Set` per pair in `bestPartner`; priorities once per pass. Cold solve, six scenes, interleaved A/B in one machine (`tmp/perf3/ab_cold.mjs`, min of 4): 540-664 ms to 323-360 ms for the six (1.7x).
* **The text table**: the engine measured its text table (`measureText` of 99 characters in 7 fonts, 60 microseconds each) when it was created, with the page's own face still loading (so with the fallback's widths), 183 ms of the first render on the 4x phone, and again after the face was ready (67 ms). Nothing read the first one (no picture is drawn before the face is ready). It is now a table that measures itself only if something reads it, and the real one is measured one font per task (T0-P3-06: 696 `measureText` calls over the first 7 s against 1,389).
* **After the tap, 4x phone** (T0-P3-04, same tap, two taps each): long tasks [85, 90] ms and none (the engine of before: [122, 785, 469] and [486, 449]); the marks are back 1.0-1.4 s after the tap at 4x (T0-P3-05; 100-250 ms on a desktop), one cross-fade per jump, 0 errors.

**Check 4 residual (item 3).** "July 1" and "Previous step" on the phone measured 266 / 380 ms on a busy machine and 70-93 / 21-26 ms alone in PERF2; they were load, not a defect: on the final tree the whole app sweep (146 activations, desktop and phone, click / tap / Enter / Space) has 0 defects, latency p50 27 ms, p95 43 ms, max 57 ms, no long task; "July 1" 41 ms, "Previous step" 47 ms, "July 2" 57 ms on the phone. Final tree, five runs of the same sweep (`tools/accept/run_pass.mjs --only 4 --input-scope app --input-parts sweep`): 0 defects in four, one defect in the fifth (phone, "July 1" by Enter: 453 ms from input to the first DOM change, event timing 24 ms, no long task; a controlled replay of tap-then-Enter on the phone shell shows the first DOM change 2-6 ms after the key on the engine of before and after, so it is a stall of that run that the harness cannot attribute); in the four clean runs latency is p50 26-28 ms, p95 42-48 ms, max 56-96 ms over 146 activations, no long task. The control (no PERF2, no PERF3) has 6 defects (Unit Roster 115 / 106 ms and long tasks of 88, 69, 68 ms, Monuments 68 ms) on the same machine in the same hour.

## 2. Phone total blocking time at 4x (item 1)

The long tasks after first paint, route by route (phone, 4x, a trace per task; `tmp/perf3/lt.mjs`, `routetrace.mjs`):

| route | what the long tasks are | what PERF3 did |
|---|---|---|
| `app` | the entry bundle's evaluation (163-195 ms; 90-120 ms of it is the bundled Mapbox GL's module init, 29 ms the engine's skins), the first React commit with `new mapboxgl.Map` in its effect (123-171 ms: `_setupPainter` 35-56, `resize` 30), Mapbox render frames with first tiles (50-110 ms), the engine's first frame (text table 183 + dataset 30-52 ms) | the engine's first frame: text table 183 ms to 0, the cold start and the dataset swaps in slices |
| `ground-remembers` | `Map` constructor 80-90 ms, the style callback (`Style._load`: ~100 layers) 130-160 ms, Mapbox render frames 50-110 ms | nothing left to take that is the page's (see below) |
| `viewshed`, `watch-together` | the `mapbox-gl.js` evaluation 280-370 ms as ONE task (JS 107-184 ms plus V8 compile, `(program)` 210 ms), the handler with the `Map` constructor 80-110 ms, render frames | prewarm, style-load and circle-layer precompile (they had none), as PERF2 did for the other pages |
| `compare` | `Map` constructor of both panes in one task 142-181 ms (forced layout 33-36 ms), render frames | the second pane in the next task |

Findings that decide what can be green here:
* **The `mapbox-gl.js` evaluation is counted only when first paint precedes it.** It is a `defer` script: when the first paint happens before it runs its 280-370 ms task is inside the TBT window, when it runs first it is before FCP and not counted. Run to run, with no code change, that flips `viewshed` between 37 and 427 ms. Making the first paint wait for it would hide the number and make the page worse for a visitor; so it is not done. It is also not reducible by the page: one classic script of 1.7 MB.
* **The Mapbox constructor, the style callback and the first render frames** are 50-165 ms each at 4x (13-40 ms at 1x): Mapbox's own work (style parse, painter set-up, first tiles); `validate` is already off for Mapbox-hosted styles. Programs are linked in advance on every map page now (PERF2, PERF3), so no frame waits for the GPU process any more, which is the part of the cost that grows with machine load.
* **The closed menu panel of `site-nav`** (opacity 0, visibility hidden) is laid out and its 1,300 characters shaped before first paint: 100-150 ms at 4x on every `site-nav` page (confirmed by hiding it: the shaping tasks drop from 85 + 52 and 104 + 52 ms to 40 + 15 and 24 + 18). It delays FCP and LCP, it is not counted in TBT (it is before FCP in most runs). Not changed: `content-visibility: hidden` moves the cost to the first press of the menu (an input, 100 ms at 4x) unless it is revealed in idle chunks, and that is a design decision (fade-out of the closed panel) for the owner.

**Honest numbers** (cold, phone, 4x, TBT as the harness measures it, interleaved, n = 7, `tmp/perf3/tbt-final1.log`; control = PERF2-less tree, p2 = PERF2 stack with the engine of before, p3 = PERF3 final): 

| route | control (no PERF2 / PERF3) | PERF3 final | runs |
|---|---|---|---|
| `app` | 326 (226-426) | 284 (255-349) | n = 7 interleaved, quiet hour |
| `ground-remembers` | 286 (228-375) | 151 (105-236) | same |
| `viewshed` | 33 (17-69) | 57 (24-217) | same: the control happened to run the `mapbox-gl.js` task before first paint in all seven (not counted), the final tree in four of seven |
| `watch-together` | 32 (15-41) | 27 (12-50) | same |
| `compare` | 83 (58-193) | 118 (20-197) | same: no difference the spread resolves; with the task attribution (`tmp/perf3/lt.mjs`, n = 3 each) the handler task went from 116-120 ms (25-28 ms forced layout) to 70-85 ms and TBT from 78, 75, 78 to 31, 102, 25 |
| earlier hour, busy machine (`tbt-final1.log`, the same cells) | app 400 / 532 / 453, ground-remembers 482 / 256 / 354, viewshed 264 / 120 / 75, watch-together 56 / 86 / 89, compare 130 / 137 / 160 (control / PERF2 / PERF3) | | spread inside a cell 40-700 ms |

Single harness runs (`tools/accept/run_pass.mjs --only 5`, one load per route, `docs/accept/PERF3-NOTES.md`): control `app` 474, `ground-remembers` 651, `compare` 415, `sandbox` 390, `watch-together` 375; final `app` 750, `ground-remembers` 559, `viewshed` 522, `compare` 319, `watch-together` 389, `immersive` 247, `cinematic-export` 324. **They are not green and they do not separate the trees**: one load is one draw from a distribution that spans a factor of ten on this machine. What the interleaved medians support: `ground-remembers` roughly halves (PERF2's precompile; PERF3 changed nothing on that page, the difference between the PERF2 and PERF3 columns of `tbt-final1.log` is noise), `app` loses about 40 ms, the other three routes were already under 200 ms by median in the quiet hour. **The phone TBT limit is therefore not shown to be met by the harness's single run; by median it is met on four of five routes and missed on `app`.**

## 3. Heap growth: the evidence behind T0-P2-11 (item 4)

Same stack with ANIM (`tmp/perf3/leak.mjs` / `leak2.mjs`, desktop 1x, 20 warm-up and 60 measured cycles of Unit Roster / Legend / Monuments open and close with a forced GC every five cycles; the loosened T0-P2-11 does 8 + 14): on the final tree DOM nodes are 1,052 and listeners 275 at every sample from cycle 20 to cycle 80; the heap goes 19.59 MB (cycle 20) to 20.21 MB (cycle 80), slope 0.0037 MB per cycle (+2.3 % over the window), and the heap-snapshot difference between cycle 20 and cycle 80 is +0.6 MB of which 361 KB are V8 code objects (JIT), 296 KB arrays of the harness's own performance observers, no HTML or Blink object. An earlier run on the tree before the engine work gave the same picture (80 cycles, 1,052 / 275 flat, slope 0.0049). So the loosening of T0-P2-11 is justified for what the test measures.

**But the soak of check 5 found a leak that test does not see, in ANIM**: 300 s of 4x playback on the tree with the engine took DOM nodes from 1,542 to 6,607 and listeners from 315 to 723 (the harness: +53 % DOM nodes, a defect), where the tree without the engine stays flat (933-983 nodes, 274-279 listeners). The heap-snapshot difference shows the dropped event cards (+294 `button[aria-label=Close]`, +447 Text nodes, +696 ElementAnimations): `host/popups.mjs` kept the placement state of every card in a `Map` keyed by the card element, and the app makes a new card element for every event. It is a `WeakMap` now: 1,057-1,123 nodes, 275-280 listeners over 300 s, heap 23-25.7 MB, and the harness soak says DOM nodes 938 -> 898, heap +8.9 % (limit 10 %; the control 8.2 %, the PERF2 dry run 10.25 %: the JIT's code objects). T0-P3-13 is the regression test (red on the tree before: 1,531 -> 2,722 nodes in 100 s).

## What remains

* **Phone TBT at 4x on `app`** (284 by median, 326 on the control): the entry bundle's evaluation (163-195 ms at 4x, of which 90-120 ms is the bundled Mapbox GL's top-level code), the first React commit that creates the Mapbox map in an effect (123-171 ms), Mapbox's first render frames (50-110 ms each), the engine's own module (29 ms) and dataset (30-52 ms). None of it is page logic that could be split; each is one synchronous call. Ways out that are decisions, not patches: load Mapbox after first paint of the app shell (a second bundle; the map is the app), or accept a 4x-CPU TBT of about 300 ms for a WebGL map app.
* **The `mapbox-gl.js` task (280-370 ms at 4x) on the map pages** counts or not depending on whether first paint comes before it; a harness that loads each page once will flip `viewshed`, `watch-together` and `compare` between about 30 and 430 ms with no change. The cure that makes the number steady (first paint after the script) makes the page worse for a visitor and is not applied.
* **`site-nav`'s closed menu panel** costs 100-150 ms at 4x before first paint on every `site-nav` page (FCP / LCP, not TBT); the options are in section 2.
* **ANIM at 4x CPU in `anim.spec` B3 / B11**: B3 (the engine against the shipped renderer, interleaved) and B11's quick limit of one long task are a coin flip on this stack, with the engine of before and after alike (old: FAIL 12 vs 23.7 fps, PASS 17.7 vs 15.9; new: PASS 12.7 vs 13.0, FAIL 12.7 vs 21.1 and 17.1 vs 16.3; B11 3-8 long tasks, the full run allows 3): the 4x playback of this stack is dominated by the app's own per-tick React commit and Mapbox, 12-17 fps with the engine and 13-24 without; the engine's own frame (step + draw + cards) is 5-9 ms at 4x. The ANIM README's 40.8 fps at 4x was measured on a stack without CLOCK, DATA and POLISH and is not reproduced here.
* **Marks after a cut at 4x**: 1.0-1.5 s (T0-P3-05) with a 6 ms slice per frame; 100-250 ms on a desktop. A bigger slice would be faster and would break the 8 ms budget the owner asked for; the solver is already 1.7 times faster. A coarser first picture (formations by order of battle) would show marks sooner but is a different picture.
* **Mapbox request budget of the long specs**: a whole `anim.spec`, `monuments.spec` or `pages-maps.spec` in one process exhausts the 300-request default and the late tests fail with "waiting for map instance"; they were run with `T0_TILE_CAP=3000`. Not changed here.
* Not registered, not in `trains.json`, nothing deployed.
