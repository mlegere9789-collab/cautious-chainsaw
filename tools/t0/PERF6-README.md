## 1. Unit Roster (check 4: 'Unit Roster', Click / Enter / Space, 52-53 ms)

**What the defect was.**  The roster mounted every unit of both armies (410 + 295 rows, about 5,000 elements).  PERF2 had cut the open to a 24-row first slice plus idle slices of 48 rows, but the rows still all ended up in the DOM, so (profile of the open on R1f) the click task was React's flush (25-43 ms), then twelve frames of 10-40 ms as the slices came in, and the engine's animation frame about 200 ms after the click contained a 40-44 ms forced layout of the rows added since the last layout: 52-53 ms in 1 of 30 opens on R1f (R1e 5 of 30).  Dropped on the way, with numbers (R1F-STATUS line 20): `content-visibility: auto` (median 143 ms, worse: the DOM is still mounted), lazy `getComputedStyle` in the pill cluster (no gain), 16-row slices (the same tail).

**The fix.**  Only the rows in view and 500 px above and below them are in the DOM (about 24 per column at open, 34-37 when scrolled; the page's elements with the roster open: about 1,050, was about 5,600).  The row is the same component (`gtHO`, PERF2's memoised `hO`), in the same order, with the same styles; the list is one scroll box as before.

* **Where a row is.**  A row's place is the sum of the heights above it.  A row that has been in the DOM has its measured height (`getBoundingClientRect`, a layout effect after every commit, so a row whose text changes with the clock is measured again).  A row that has not is given the median of the measured rows of its class (class = has a commander line x has a placement note: the commander line and the note are what make a row 35, 49 or 63 px high); until a class has a sample, 35 / 49 and, for a class with none, `(h - 7) * 2 / 3 + 7` of the other.  The estimate is replaced by the measured height as the rows come in; **in idle slices** (`requestIdleCallback`, 300 ms timeout, 10 rows, in order from the top) the rows that were never in the view are rendered once into a hidden, absolutely positioned, `inert` container of the box's own width and measured there, so that after about 1-3 s the list's height and every row's place are exact (the scroll bar and "where does row 300 sit" are then the control's to the pixel; before that they differ by the few rows whose height differs from the median).  The container is removed when every row is measured (or when a measurement gives zero heights, e.g. a hidden panel).
* **Scroll position.**  The box's own scroll position is never moved by the code unless a height ABOVE the row at the top edge changed (a measurement of rows that were shown before, or the width of the box changed): then the row at the top edge is kept where it was (`scrollTop += offset change`); the browser's scroll anchoring is switched off for the box (`overflow-anchor: none`) so that the two do not both correct.  When the box was scrolled to its bottom it stays at the bottom (the End key).  A row that was never shown does not move the scroll position when it is measured (it was not seen).
* **Semantics.**  The box stays the focusable `role=group` with its name ("Union units" / "Confederate units"), so the keyboard scrolls it as before (arrows, Page Up/Down, Home/End: the same rows at the same places as the control in the test); the rows are `role=listitem` with `aria-posinset` and `aria-setsize` inside one `role=list`, so a screen reader announces "item 37 of 410" for a row (the control had unnamed generic divs); the two spacers and the measuring container are `aria-hidden`.  `Ctrl+F` finds only the mounted rows (the 700 rows were never searchable by anything but the browser's find; the Search and Find Unit panels of the app are the way to find a unit).
* **Not changed:** every look (the same row component and styles), the header counts, the order, the dialog focus (PERF2's next-frame focus), the clock's updates of the rows, the phone Tools sheet's roster (same component), the "Order of Battle" overview (a different component, not on the input matrix).

**Test updated on purpose:** `T0-P2-05` (perf2.spec) asserted "every row is in the DOM after 4 s"; on a tree with PERF6 (the list has a `role=list`) it asserts what the virtual list promises instead (rows say item k of N with N = the header's count, a screenful plus overscan is mounted, item 1 at the top, item N flush with the bottom after scrolling to the end); on a tree without it the old rule still applies.  `T0-P2-11` (open/close leaves DOM nodes and listeners flat) is unchanged and still passes.

## 2. /compare "3D Terrain" (check 4: Enter, 51 ms; page group `PG-zperf6`, `tools/t0/r1g/gen_terrain.py`)

**What the defect was.**  Found once in run D pass 2 (rAF callback in mapbox-gl.js, 16 ms after the key; 20 warm mouse toggles later: nothing).  It is reproduced every time when the visitor first changes the left map to a style with fog (Dark, Light: the acceptance matrix presses the style buttons before it reaches 3D Terrain) and then switches the terrain off with Enter: the map is still tilted, the style has fog, the terrain is off.  The units layer (a circle layer) then needs the circle program **with fog and without terrain**, which nobody had made: Mapbox's own precompiler skips circle and symbol layers, and `GTBG_PRECOMPILE` (site-nav.js) queued `{terrain off, fog off}`, `{terrain on, fog off}`, `{terrain on, fog on}` but not `{terrain off, fog on}`.  Its first draw links the program inside Mapbox's render frame (`circle` -> `uploadCommonUniforms` -> `setFogUniformValues` -> `Program._ensureReady` -> `getProgramParameter`, the main thread waits for the GPU process).  Measured with a hook on `getProgramParameter` and on the painter's `getOrCreateProgram` (program `circle`, defines `FOG,SCALE_WITH_MAP,DEPTH_D24`, `precompiled: false`, created in the Enter window): 12 of 12 cold loads link exactly that one program in the Enter window, 18-38 ms each (sum 262 ms, task median 29 ms, max 40 ms on a quiet machine; the first time a GPU driver cache is cold it is the 51 ms of the owner's run).  The satellite style (no fog) never needs it, which is why the 20 warm toggles on the default style did not show it.  Dropped on the way (nothing to slice): the toggle's other frames are Mapbox's own render work (terrain update, tile coverage, 4-12 ms each, one first frame of 13-30 ms); a CPU profile shows no single DEM decode, upload or hillshade step in them, and the source, the terrain and the tilt are already three separate steps (PERF2: the pressed state is painted first, the terrain follows in the next task).  The owner's slicing idea (source first, terrain a frame later, tilt a frame after that) was built as a scratch variant of compare.html and measured against the fixed build, interleaved, n = 30: click med 21 / q90 25 / max 31 ms (sliced) against 20 / 25 / 32 (not sliced), Enter 8 / 9 / 10 against 6 / 12 / 13: the first terrain frame costs what it costs, slicing the three steps moves nothing, so the page is not changed.

**The fix.**  `PERF6-nav-terrain-fog-variant` (site-nav.js): in the terrain stage of the precompile queue, with fog in the style the circle and symbol programs are also queued as `{terrain off, fog on}` (idle slices, never inside an interaction, like the other terrain variants).  Nothing changes for a style without fog, and the picture is unchanged (the same programs are drawn, only linked earlier: T0-P6-07 compares the settled pictures with the control pixel by pixel).  Every other Mapbox page that queues the terrain variants gets the program too.

**Tests.**  `T0-P6-06` (the hook counts the link waits in the window after click / Enter / Space in Dark and Light: none above 8 ms, no task of 50 ms; red on R1f), `T0-P6-07` (settled picture with terrain on, off, on again: 0 differing pixels against the control).
